# lane/apple-fast-isotonic-knn: isotonic parallel PAVA; LLE / LOF k-NN through fast_mma_knn (PLAN.md item 8)

Written without a Mojo toolchain (cloud peer); the first M3 build is the compile check.
Every switch defaults OFF and is compiled under FAST + Apple only; IDENTICAL compiles main's code unchanged.
Merged with origin/main (hr2 lanes) on 2026-10-02: main's LLE standard path (`_knn_mats` -> `graph_knn` cell ->
`barycenter` -> `graph_lle_iw`, I - W resident) and its `knn_sq_tiled2_kernel` win; the FAST changes sit on top.

Causes:
- isotonic (12-16x): `x_linear/isotonic.mojo:129` `if not t.lead(): return`: the sort of a million rows (`_iso_sort`, :93, one device thread), `_make_unique` (:157), PAVA (:190) and the trim (:236) all on one thread of one block.
- lle (taxi 14x, Istella 6.3x on the 0.8.34 board): main now selects on the device (`graph_knn` over the n x n `sqdist`); the FAST arm skips the n x n matrix (n^2 floats built, read and selected over) for the fused per-row k-NN.
- knn-imputer (taxi 43x; fit 100,000 rows, 20,000 queries, 10% cells missing): `knn_impute_split_kernel`, 8 scalar threads per missing cell scanning every fit row from a shared tile, one feature per shared load; no host loop and one upload per op (the Python path is nan_cells + one impute op). The TILED2 define is the register-tiled form of the same scan (above). fast_mma_knn cannot take it as is (the distance depends on the pair's presence mask); a masked four-dot-product MMA form (u = [a', a'^2, ma], v = [-2b', mb, b'^2], present = ma . mb) is the next step if TILED2 is not enough.
- lle, where the clock really is: after the k-NN (fused here) and `barycenter_kernel` (x_decomp/device.mojo:923, already one thread per point: nothing to batch), `_lle_smallest` (python/mojolearn/_expansion_decomp.py:3944) factors the DENSE n x n F0 with `k.lu` (10,000^2: an O(n^3) getrf), then runs subspace iteration with dense n x n products and a Jacobi SVD per step; `graph_lle_iw` also writes the dense n x n I - W. scikit-learn's arpack works on the sparse I - W (n x (k + 1) nonzeros). A FAST route needs a sparse shift-invert (sparse LU / CG on F^T F) or LOBPCG on the sparse operator: a new solver, not a switch; not written blind here.

A/B lines (`isotonic-knn.txt`, light form: one alternation, 2 rounds, one dataset first, no -ident lines):
`ik-iso-par-istella` (define, two x_linear builds), `ik-iso-pair-istella` (PAR vs PAR + PAIRMERGE), `ik-imp-t2-taxi`, `ik-lle-knn-taxi` (env switch, one build), `ik-lle-mma-taxi` (the define A/B with `MOJOLEARN_LLE_FAST_KNN=1` on both arms: the route only matters once the lists come from the device), `ik-lof-mma-taxi` (the route on a lane that already takes `knn_sq_tiled`). The second dataset follows a win.
Keep rule: a switch becomes the FAST default when its arm is faster on the M3 and held-out quality stays within FAST's run-to-run spread; then the switch goes and the arm is the code.
Compile risks to watch: `x_linear/isotonic_fast.mojo` (UInt64 key buffers, comptime-parameter scan kernels, `Tuple[Int, Int]` helpers, the PAIRMERGE `comptime if` around a host `for` of launches), the function-scope import of `neighbors.impl.detail.fast_mma_knn` into the x_neighbors binding, and `knn_impute_tiled2_kernel` (eight threadgroup arrays, 27,520 bytes, gated by `lib_smem_page_fits_for`; `InlineArray` register blocks as `knn_sq_tiled2_kernel`'s).
