=== WHAT IS HAPPENING (measured, do not re-derive) ===

The ten [B, n_heads, L, S] attention arrays are allocated at ONE element for
the fused path and GROW ON DEMAND the first time a layer takes the eager
path. Once grown they are NEVER RELEASED while the session lives.

A 700-step run steps 16.949 -> 34.397 GB and 0.207 -> 0.44 s a step, one
layer at a time, reaching 12/12 layers and eager_bytes = 17,314,086,912.
That number was predicted from the formula BEFORE the run and matched
exactly. Each increment is 1,442,840,540 B, which is exactly one layer:
forward 3*B*H*L*S + L*S floats = 620,756,992 B plus backward 4*B*H*L*S + L*S
= 822,083,584 B, the 36 B shortfall being the nine one-element placeholders
that stop counting once a layer grows. The device agrees independently at
1,376 MB per grown layer against one layer's set of 1,376 MiB.

`aexp` is NOT part of the growth. It is full from step 0 via the DEVIATION
2652 exp stash. Counting it gives 19.730 GB, which is 13.1% too high and is
the wrong answer. Report it apart from the other three or the result becomes
illegible.

THE TRIGGER IS NOT IDENTIFIED. Two candidates, both in
transformer/impl/llama/fused_attention.mojo, declared at lines 144 to 149:
FUSED_REFUSED_REGIME (1) and FUSED_CORNER (2), against FUSED_RAN (0).
`regime_product_ok` is hd*a_max*b_max < 2^100 and a healthy run never nears
it, so FUSED_CORNER is the likely one, BUT THIS IS UNPROVEN. Do not assume
it and do not build on the assumption.

1. INSTRUMENT THE TRIGGER FIRST, AND NAME IT.
   `stages.attn_materialized` already exists in

   backward_eager_cells, the matching *_bytes, layers_grown_forward,
   layers_grown_backward, layers_full_aexp, layers, eager_bytes and

   that "the arrays are grown" is separable from "the eager path ran this
   step". Then run 700 steps and NAME the trigger with status counts.
   DO NOT PROCEED TO 2 OR 3 ON A GUESS.

2. STOP PAYING TWICE.
   transformer/impl/llama/modeling_llama.mojo:3581-3594. `fused_forward_launch`
   runs, and THEN, if its status != FUSED_RAN, `attention_eager_core` runs as
   well. The fused kernel has ALREADY been launched and paid for. That is why
   the cost is 2.13x rather than the eager path's own speed. Either make the
   decision BEFORE launching the fused kernel where the status is predictable,
   or make the fused launch cheap to abandon.

3. BOUND OR RELEASE THE ARRAYS.
   Once a layer has grown, 1,376 MiB per layer is held for the life of the
   session. Either release after the step or cap what a session may hold.
   This is what makes batch > 1 die: batch 4 OOMs at EXACTLY step 210, the
   same index at which batch 1 begins climbing. Throughput saturates at batch
   4, so fixing this plausibly unlocks a second multiplier on top of the
   2.13x. Measure that, do not assume it.


=== CONSTRAINTS, ABSOLUTE ===

BITWISE IDENTITY. IDENTICAL FP32, no tensor cores, no TF32, the RN-FMA then
FTZ-multiply seam kept, leaf boundaries and fold topology kept. Any arm that
changes one output bit is a DEFECT, not an optimization. Bits must stay equal
on Apple, NVIDIA and AMD.

A VERIFICATION THAT CANNOT FAIL IS NOT A VERIFICATION. For every check, break
the thing deliberately and WATCH THE CHECK FAIL before believing a pass.
Print the matches, not the count.

WATCH FOR A BLIND SHAPE. At head_dim=8 the fused kernel is not instantiated
at all (`fused_supported_head_dim` admits 16, 24, 64, 128), so BOTH arms fall
back and any comparison is a pass-shaped result that means nothing. This was
caught once already. Use head_dim=64.

REGISTER PREDICTIONS BEFORE RUNNING, with numbers, and name the falsifying
outcome in advance. Report INERT as INERT, never "bits unchanged". Do not
attribute a cause you have not isolated. If an arm is underpowered, say so
and do NOT draw a conclusion from it in the same breath.

COMMIT AND PUSH TO YOUR BRANCH BEFORE ANY LONG RUN. A lane lost its entire
contribution once as untracked files in a dead session's scratchpad. Never
`git stash` (stashes are shared across worktrees). Never `git add -A`. Check
`git rev-parse --abbrev-ref HEAD` immediately before every commit.

NEVER CANCEL AN OWED RUN. A cancel hands the whole fetch, decode and build
cost to the next attempt.
