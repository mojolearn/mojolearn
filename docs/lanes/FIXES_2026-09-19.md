# What was fixed on 2026-09-19, and what it cost to find

Nine defects, from `79ea82b49` to `341b8f8bc` on `main`. Every one was found
by a tool this repository already had; none needed a new measurement
apparatus, and the one new checking tool written that day was DELETED the
same day for giving false confidence (§10).

## 1. Three decompositions were computed but not reachable

`PCA`, `TruncatedSVD`, `Nystroem`, `SpectralClustering`, `KernelRidge` and
the ARIMA least squares had run a Householder QR, a symmetric Jacobi
eigensolver and a one-sided Jacobi SVD for months, each gated as somebody's
internal step. A caller who wanted the decomposition itself had no way to
ask. Now `mojolearn.linalg.qr(a, mode="r")`, `.eigh(a)` and `.svdvals(a)`,
carrying numpy's names and numpy's meanings, adding NO new arithmetic --
`decomposition/host/linalg_public.mojo` validates, calls the shipping host
oracles and permutes. What this tree does not compute is refused BY NAME: a
Q factor (never formed anywhere), an `svd` returning U (the Jacobi's left
basis belongs to R, not to `a`), a wide matrix (DEVIATION 593).

## 2. THE JACOBI ROTATION HAD NO NEGATIVE CONTROL

The first sabotage run of the new `linalg-eigh` lane came back BYTE-
IDENTICAL. Reached and INERT, which in a column reads exactly like coverage.

`pca_oracle.mojo`'s only sabotage arm was `host_gram_splitk`'s, which the
eigensolver reaches only when something upstream built its matrix with a
gram product. `linalg.eigh` does not. So `_rot_sub` / `_rot_add` -- where
the rotation's arithmetic actually lives -- had no arm at all, and EVERY
consumer of it (PCA, TruncatedSVD, Nystroem, SpectralClustering, the GP, and
the one-sided SVD, which imports the pair) moved only because a fold ABOVE
it moved. Both now have arms; the fold walks its lanes descending, the
rotation splits the FMA.

A fold arm alone did NOT fix it -- that fold feeds only the convergence
threshold, which a well-separated spectrum clears in the same sweep either
way. Its comment says so rather than implying it was the fix.

## 3. `DistributedIVFIndex` could not run on a CPU at all

Not a missing lane -- a missing implementation. Its workers call
`ivf_flat_partial_search` and `ivf_finalize_distances`; neither IVF host
binding registered them, and `_parallel_pool.CPU_OPERATIONS` did not admit
the three operations. An in-tree test, `test_bindings_register_the_gpu_names`,
WAS ALREADY FAILING ON MAIN for exactly this reason. The host search arm is
implemented, both entries registered, and `par-ivf` added -- identical at 1,
2 and 8 shards.

## 4. `bpe-trainer` was inert under its own sabotage define

`MOJOLEARN_TOKENIZER_HOST_SABOTAGE` reverses `bpe_encode`'s ids, and
`bpe-trainer` never encodes. Added `MOJOLEARN_BPE_TRAINER_SABOTAGE`; all
four tokenizer lanes now move. Same class of defect as §2, found the same
way: by watching the negative control instead of trusting it.

## 5. Host-surface drift stranded three lanes

`lane/bpe-builder-native` (2026-09-18) compiled `bpe_train`,
`bpe_trained_sizes` and `bpe_trained_copy` into the tokenizer binding and
added them to `exports` and `host_modules` -- and nobody extended the
hand-written `training_lanes` tuple. `covered_lanes()` therefore omitted
`bpe-trainer`, `bpe-vocabulary` and `tokenized-corpus`, `lane_applicability`
called them degenerate, and `verify_lanes.py` REFUSED lanes whose binding
was built, loaded and producing hashes. The code moved and the tuple did not.

## 6. A CPU column was being charged for multi-GPU lanes

A `par-*` lane is a multi-device driver whose claim is that a TWO-DEVICE
column hashes equal to the one-device column cell for cell. On a CPU column
that claim is not false, it is NOT EXPRESSIBLE -- and the harness has always
said so when refusing one. `verification_matrix.py` counted them anyway:

    CPU-axis gap heading                 reported   actually owed by CPU
    Sabotage not seen to move a build          39                      0
    No CPU verifier declared                   36                      4

Thirty-six inexpressible claims on top of three real ones (§5) -- a
ten-to-one noise ratio that hid them for a day. The rule now lives in the
tool, which holds `par-*` out of both CPU-axis counts by construction, and
in `docs/CPU_IDENTITY_AND_MULTI_GPU_PLAN.md`, which already said it in prose
and was ignored. A floor in prose is not a floor.

## 7. The 27 gap registries were misshapen

`NOT_IMPLEMENTED.tsv`, 425 rows across 27 files. `gbdt/` used a DIFFERENT
schema (`file, symbol, why`) so column 2 held a C++ SYMBOL where 26 files
held a STATUS; seven files declared no schema at all; `decomposition/` line
17 carried two rows on one line, so one gap had no `what`; `solver/` line 5
was missing its `why`; and `hierarchy/` called `build_mr_linkage` NOT
IMPLEMENTED for the 19 days after it shipped, in a file whose own docstring
quotes that row and answers it. `tools/check_not_implemented.py` refuses all
four shapes; run against the pre-fix tree it reports 31 problems.

## 8. The linalg lanes' reference debt, incurred and paid the same day

Adding the three lanes to `training_lanes` made them PUBLIC REFERENCE LANES
with no cell in the shipped table, so
`test_public_reference_lanes_are_derived_and_every_pending_reason_is_true`
failed from that commit. They are in `PUBLIC_PENDING_LANES` as
"no reference" now, which is the true statement:

    section                     verified  divergent  owed  refused
    estimators (pca,tsvd,kde)        108          0     0        0
    linalg (3 new + cholesky)          0          0    27       45

They are bit-reproducible on CPU and sabotage-proven. The CROSS-VENDOR claim
this tree exists to make is NOT established for them until one GPU column
carries them.

## 9. AN UNWRITTEN BUFFER WAS REPORTED AS A CONVERGENCE FAILURE

`jacobi_eigh_kernel` writes `info[0]` as 1.0 converged / 0.0 not converged.
**0.0 is also what unwritten memory reads.** The three device callers left
the buffer at whatever it was allocated with, so "the kernel reported
failure" and "the kernel never ran" were THE SAME READING.

It surfaced as a refusal that contradicts itself:

    lstsq_eig: the device Jacobi did not converge in 15 sweeps on the
    16 x 16 Gram matrix; ||offdiag(A^T A)||_F / ||A^T A||_F is still 0.0

A ratio of 0.0 IS convergence. The kernel cannot produce that pair:
`converged` is false only when `2*off > tol^2 * fro2`, which forces the
reported `rel` above tol, i.e. 1e-7, never 0.0.

`JACOBI_INFO_UNWRITTEN = -1.0`, a value the kernel never stores, is filled
before the launch and the three cases are now separated by name. Fixed in
`lstsq.mojo`, `svd.mojo`, `lstsq_min_norm.mojo`. `glm/host/glm_oracle.mojo`
needed nothing -- it reads a real `Bool`, which is why this never appeared
on the CPU route.

## 10. A check that gave false confidence, written and deleted the same day

A `check_public_surface_covered.py` was written to compare `__all__` against
the lane registry. It was DELETED within the hour, for three reasons that
are worth keeping: it passed on a mere MENTION of a class name anywhere in
the harness, so its green light meant "someone typed this"; its allow-list
was hand-maintained, so it drifted exactly like the thing it audited; and it
read `__all__`, so it could never see an algorithm that was never exposed.

`tools/verification_matrix.py` already did the job properly -- it reads the
tree, and it counts a sabotage ONLY when a committed pair of columns
disagrees, because this repository has shipped sabotage that could not fail
more than once. It then immediately found §2 and §8.

The lesson is not "we lacked a tool". It is that a worse duplicate of an
existing tool is a liability, and that the existing one had been telling the
truth to nobody.

# Why the builds cost what they cost

The instinct that this should be light is correct, and the split is:

| build | per family | 
|---|---|
| HOST (CPU) binding | **~5 s** |
| GPU (Metal AOT) binding | **~100 s** |

A full host set, all 32 families, is about **3 minutes**. The 16 stale GPU
bindings would be about **27 minutes**, and the cost is Metal compiling
every GPU kernel ahead of time.

**Every fix above needed only host bindings.** Nothing in §1-§10 required a
GPU build except §9's compile check, which was one family.

That is the tiering this project already set, and it should be followed
rather than re-litigated:

- **routine** -- only the affected lanes, on CPU, in seconds
- **broad** -- a full sweep on RENTED CPU, sharded across pods
- **GPU columns, Apple included** -- ONCE PER RELEASE

**Metal never runs a sweep**, only a lane's own new cells. A local
`verify --all` on the Metal backend is the heavy thing the tiering exists to
prevent; it was run once on 2026-09-19, took 1296 s, and its 1113
"divergent" parts were entirely the Sep 13-14 bindings being stale against
today's source -- not arithmetic. Rebuilding ONE family and re-running the
comparator self-test proved it:

    untouched   3d1d7c30b12d9872  vs reference 3d1d7c30b12d9872  -> IDENTICAL
    perturbed   dd42c9b607526efe  vs reference 3d1d7c30b12d9872  -> DIVERGENT
    RESULT: THE VERIFIER WORKS ON THIS MACHINE.

So the answer to "do we need to shrink the bindings and the testing
further?" is NO for day-to-day work -- it is already seconds -- and the way
to keep it that way is to not reach for the GPU sweep outside a release.

# Later the same day: three more defects, and three of my own

## 11. The zero-kernel gate was OFF on every identical build

20 of 22 GPU build scripts `export MOJOLEARN_SKIP_BUILD_GATE=1` FOR
THEMSELVES on the identical and deterministic tiers, and the skip then turned
off ALL THREE checks. So the gate that exists because a zero-kernel artifact
shipped for hours in August ran only on `fast` builds -- never on the
identical ones whose cross-vendor claim is the product. Only the
kernel-launch smoke needs the rest of the package; the AIR blob floor
(`strings`) and the minos check (`otool`) import nothing and cost
milliseconds. They run unconditionally on Darwin now. Proven to discriminate
on artifacts already in the tree: gbdt 143 blobs and arima 10 pass, both host
bindings read 0 and are REFUSED.

## 12. MY SHARDER MANUFACTURED 1049 DIVERGENCES

I wrote `tools/verify_sharded.py` to cut `verify --all` from 21.6 minutes,
ran it four ways against the Metal backend, and read its 1049 DIVERGENT parts
across 40 lanes as a finding. They were all artifacts. The same lanes SOLO:

    gmm, gp-matern12, rbf-sampler   4-way sharded -> 36 DIVERGENT parts each
    the same three                  solo          ->  0 DIVERGENT, VERIFIED

This project already knew concurrent Metal jobs on one M4 return NaN,
constant and zero outputs. Four shards on one GPU is four concurrent Metal
jobs. I built the thing the rule forbids. It also SAVED NOTHING -- 1163 s
against 1296 s serial -- because the GPU is the serial resource. The tool now
refuses to shard without `--cpu-only`.

## 13. MY OWN DESIGN ERROR: the three decompositions had no GPU path

I exposed `qr`, `eigh` and `svdvals` calling `_host_load()` UNCONDITIONALLY
on every box, GPU boxes included, and wrote a docstring justifying it. In a
GPU-FIRST library that means they can never have a GPU column, never be
checked across vendors, and never join the claim the project exists to make.
A Metal round recorded `vendor: "arm64"` instead of `apple-m4` -- the host
binding had served it. Device doors are being written; the kernels
(`qr_factor`, `one_sided_jacobi_svd_kernel`, `jacobi_eigh_kernel`) already
existed, so it is a door, not arithmetic, and `Cholesky` already shows the
shape: one class, `_door()` picks device on a GPU install and host on a
CPU-only one.

I briefly declared them `PUBLIC_HOST_ONLY_LANES` instead. That was reverted:
it would have cemented the mistake into the registry and made the matrix stop
asking for the thing we actually want.

# The fast tier is narrower than it looks -- measured

`--fixtures base` runs all 251 lanes in **191 s** against **1296 s** for all
nine, with 0 divergent. But base is NOT a cheap approximation of the full run:

    lanes where every other fixture's reference hashes EQUAL base's:    2
    lanes where at least one fixture DIFFERS from base:               234

A fixture whose hashes match base cannot catch anything base misses; one that
differs is exercising a distinct path. 234 of 236 lanes have at least one. So
the 6.8x costs real coverage on 99% of lanes:

- **`base`, 3.2 min** -- did this change break something obvious. Every commit.
- **all nine, 21.6 min** -- the actual identity claim. Before anything is believed.

# Build cost, measured rather than extrapolated

    HOST binding            ~5 s      all 32 -> ~3 min
    GPU binding, warm cache  6-9 s
    GPU binding, cold        61-100 s (scales with kernels unique to the family)
    all 19 GPU bindings      5 m 48 s

An earlier estimate of 27 minutes was extrapolated from ONE cold compile and
was wrong by 5x; `.mojo_cache` is content-addressed and the families share
`core/`. `gbdt` at 61 s dominates, being the largest binding in the tree.
