## 2. The one building block most of this rests on: the identical fp32 GEMM

`gemm/neural_dispatch.mojo:207 identical_gemm[allow_vendor, ROLE](ctx, c, a, b, m, n, k, op)` with `OP_NN`, `OP_NT`,
`OP_TN` (`gemm/IDENTICAL_FP32_CONTRACT.md:62-66`), profile `mojolearn.identical.gemm.fp32.v1`, bit-identical on
Metal / PTX / HIP at 62 shapes x 8 plans (contract STATUS). It runs scalar `fma` chains on NVIDIA and
`v_mfma_f32_*x*x1f32` (K = 1, so each step is exactly one product plus one add) on AMD
(`gemm/checks/gemm_identical.mojo:2894, 3442-3468`). No TF32, no reduced-mantissa accumulation anywhere
(contract :143-165). On the board it is at parity with torch bf16 for 4096^3: 56.4 ms whole-clock including three
64 MB copies, so its kernel rate is at least 2.4 TFLOP/s and probably 3-5 (nothing measured kernel-only; the
contract itself says "No performance figure", :740).

Two gaps in it that the dense-LA work needs (Section 3), and that the GEMM lane should add first:
- **strided / sub-block operands** (`lda`, row and column offsets): blocked LU, QR and tridiagonalization update
  trailing sub-matrices. Today's entry takes contiguous `m x k` buffers, so a caller must pack and unpack
  (an extra read and write of the sub-block per panel; at 256 panels of an 8192^2 matrix that is 2 x 256 x the
  trailing area ~ 90 GB of traffic, 100+ ms). The contract's batch-composition invariance (each output cell's fold
  is a pure function of k) means a strided view does not move bits; it is an API addition, not a numeric one.
- **a `beta = 1` accumulate form** (`C -= A B`) so the trailing update does not need a separate subtract pass.

Everything below says "GEMM" meaning this entry, never `linalg.matmul` (a closed vendor library; IDENTITY_PATHS
rows 24, 27, 28).

## 3. Dense square linear algebra: eigh, LU, Cholesky (program 1)

### 3.1 eigh (n = 4096, UPLO = L): 1,983,580 ms on the board; torch 80 ms

**(a) Today.** `linalg.eigh` -> `_Kit.eigh` -> `x_decomp_eigh` -> `DevExec._eigh_par_on` (`x_decomp/device.mojo:3010`).
Two-sided round-robin Jacobi (`x_decomp/jacobi_par.mojo:1-35`): 4095 rounds per sweep, each round two launches
(`eigh_par_cs_kernel` grid 8 x 256; `eigh_par_update_kernel` grid 49,152 x 256, half the h x h threads idle,
`jacobi_par.mojo:80-96`; launches at `device.mojo:3062-3071`). Every round rewrites all of A and V (64 MB each)
through scattered, uncoalesced 2x2 gathers (`rr.mojo:63-136`): O(n^3) memory traffic per sweep with no blocking.
No host sync per round (`IDN_XD_NO_WAIT`, :202); one 3-scalar readback + synchronize per sweep (`:1835-1863`), with
`rr_row_off` walking each row serially on one thread (`rr.mojo:140`). Up to `RR_EIGH_SWEEPS = 60` (`rr.mojo:200`);
8-12 sweeps means 65k-100k launches. Classification: a per-step launch chain (not serial, but launch- and
bandwidth-bound: ~8k launches and ~1 GB of scattered traffic per sweep). Estimate 20-60 s on the L40S, unmeasured.
The 1,984 s row is the deleted one-block solver, as the code comment itself says (`_linalg_impl.py:1376-1385`).
A block-Jacobi variant exists but is off after an unconverged pivot on the n = 4096 rank-one fixture
(`rr_block.mojo:44-51, 71-79`; dispatch `device.mojo:3042`). FAST on NVIDIA runs the same Jacobi.

**(b) Opponent.** torch `linalg.eigh` = cuSOLVER `syevd`: blocked Householder tridiagonalization (`sytrd`: panels of
reflectors via `latrd`, trailing rank-2k update as one `syr2k` GEMM per panel), divide-and-conquer on the
tridiagonal (`stedc`, Cuppen's split + secular equations, O(n^2) with GEMM-shaped merges), back-transform
`ormtr` (compact WY, GEMM-shaped). About 4/3 n^3 (tridiag) + 2 n^3 (back-transform) ~ 230 GFLOP at 4096, mostly
in GEMMs on tensor-core-free fp32 cuBLAS: 80 ms.

**(c) Design (GPU-only, parallel, same bits NV/AMD).** The algorithm already exists in the tree for FAST + Apple:
`x_decomp/eigh_tridiag.mojo` (1,124 lines, `eigh_td_on` at :937): Householder tridiagonalization in `TD_NB = 32`
column panels (4 grid launches per column: `td_col_kernel`, `td_gemv_kernel`, `td_p_kernel`, `td_w_kernel`; one
`td_syr2k_kernel` 32x32-tile rank-2k update per panel), eigenvalues by Sturm-count bisection in double-float
(one thread per eigenvalue, `td_bisect_kernel`), eigenvectors by Dhillon's twisted factorization (one thread per
eigenvalue, `td_vec_kernel`), back-transform in compact WY (`td_gram_kernel`, `td_tfac_kernel`, `td_bt_*`). One
readback decides the refusal (clustered eigenvalues below `TD_GAP_MIN_REL`), falling back to the Jacobi. M3: 43,766
-> 700 ms (`:63`). It is gated `NUMERIC_FAST and has_apple_gpu_accelerator()` (`:66-69`).

Promote it to IDENTICAL on NVIDIA and AMD with these pins:
1. Every cross-thread fold in it (the block partial norms in `td_col_kernel`, the partials fold in `td_gemv_kernel`,
   the `p . v` partial, the Gram and `Y^T Z` folds in the back-transform) gets a fixed partition that is a function of
   n only (a fixed chunk count, like the gbdt C = 4096 rule) and a fixed tree order; no `block.sum` with a
   hardware-width lane fold (IDENTITY_PATHS rows 4-7). Bisection and the twisted recurrences are per-thread serial
   chains already: identical by construction given identical T.
2. Replace `td_syr2k_kernel` and the back-transform products with `identical_gemm` calls (`OP_NT` for
   `A -= V W^T + W V^T`, `OP_TN`/`OP_NN` for `Z -= Y (T_p (Y^T Z))`). This is where the n^3 lives; the strided-operand
   addition of Section 2 avoids packing.
3. Keep the refusal: a clustered spectrum falls back to the (identical) round-robin Jacobi on both vendors; the
   decision is a pure function of T's bits, so both vendors take the same branch. For the board's matrix
   (Wigner + 2 sqrt(n) I) eigenvalue gaps are O(1/n) relative and the one-shot vectors hold; the Apple run shows
   orthogonality 1.7e-6 (`:58-61`).
4. Quality note: the tridiagonal path's eigenvalue error is 4.3e-7 against numpy 3.5e-8 (`:60`, `:86`); the
   double-float panel variant (`EIGH_FAST_PANEL_DF`) fixes the trailing-matrix rounding and should be the IDENTICAL
   default if its cost (an n x n low-word buffer, 2x GEMV traffic) stays under ~20%.
5. Later (strong model, optional): tridiagonal divide-and-conquer to drop the clustered-spectrum refusal, and a
   two-stage (band) reduction so the rank-2k updates become wide GEMMs.

**(d) Expected.** 4096 columns x 4 launches = 16k launches (~80-160 ms of launch floor at 5-10 us each) + 128
GEMM-shaped rank-2k updates (92 GFLOP, 30-60 ms) + bisection/vectors (ms) + back-transform (137 GFLOP as GEMM,
40-70 ms): roughly 0.3-0.5 s on the L40S, i.e. 4-6x torch instead of ~500x. Reducing the per-column launch count
(fusing `td_p` and `td_w`, or a 2-launch column step) takes it toward 0.2 s. **Bits change** (new algorithm): allowed
within a version; NV and AMD and the host column change together; `tools/hooks` identity check on the n = 4096
fixture before merge.

**(e) Effort.** M for the promotion with pinned folds (strong model, because every fold is an identity decision);
S extra for the GEMM substitution once Section 2's strided entry exists. **(f) Nothing waits on Modular.**

### 3.2 LU (n = 8192, B 8192 x 64): 264,000 ms on the board; cupy/torch 36 ms; really 4,516 ms

**(a) Today.** `solve` -> `x_decomp_lu_gesv` -> `DevExec.lu_gesv` (`device.mojo:4223`): `launch_lu` (`:2512`) then
`launch_lu_solve`, one sync at the end. `launch_lu` is blocked right-looking with partial pivoting, `LU_PANEL_NB = 32`
(`:741`), 256 panels. Per column five launches (40,960 per factor): `lu_pivot_part_kernel` (<= 4 blocks x 256 reading
column k at stride n), `lu_pivot_fin_kernel` (1 x 256), `lu_swap_cols_kernel`, `lu_l_kernel`, `lu_update_panel_kernel`
(TPB 128, `:345`). Per panel two launches: `lu_swaps_trsm_kernel` (one thread per trailing column walking a serial
32 x 32 triangle) and `lu_trail_rb_kernel` (grid up to 127^2 blocks x 256, 4 x 4 cells per thread, scalar `fma`
through shared memory, `:986-1052`; no matrix units). Solve: `lu_perm_kernel`, `launch_trs_tri` in 128-row blocks
(~256 launches, `:2138-2165`), `lu_finish_kernel`. ~41.5k launches, no inner host sync, so the 4.5 s is: ~0.2-0.4 s
of launch floor, and the rest a trailing update running at roughly 150 GFLOP/s of scalar fp32 (2/3 n^3 = 366 GFLOP
-> ~2.5 s) plus the serial triangle chains. Classification: an unblocked-rate trailing update (the kernel is blocked
in name but runs 4x4 register tiles without the GEMM's staging) plus a 5-launch column chain. The 264 s row is not
this code: it is a host-column artifact of the 0.8.25 run (the number equals one CPU thread's rate; the GPU box gets
the host binding only on a CPU-only install, `_backend.py:2339-2357`), consistent with the Oct-1 measured 4.5 s.
`lu_solve` as a separate call re-uploads the 256 MB LU (`:2868`); the lu-factor lane pays that. A fused one-block
panel step was refused by `tools/hooks/no_host_routes.py` ("one-block-n": a one-block launch over a runtime size,
:177).

**(b) Opponent.** cuSOLVER `getrf` = recursive panel (`getrf2`, 32-128 columns, warp-level pivot search with
`idamax`-style reductions), `laswp` row swaps, `trsm` on the panel's row block, and one `gemm` trailing update per
panel on cuBLAS SGEMM (fp32 CUDA cores, ~20+ TFLOP/s); `getrs` = `laswp` + two `trsm`. 36 ms for 366 GFLOP is
~10 TFLOP/s effective.

**(c) Design.** Keep the algorithm (right-looking blocked LU, partial pivoting with the existing deterministic
pivot rule: largest |a|, ties to the smallest row index), change the three things that cost:
1. **Trailing update through `identical_gemm`** with the strided sub-block entry: `A22 -= L21 U12` (m = n = trailing,
   k = 32 or, better, 128). A fixed fold along k inside the GEMM is the only summation; bits change once (the fold
   order of the update differs from `lu_trail_rb_kernel`'s) and are then identical on both vendors by the GEMM
   contract. At 3-5 TFLOP/s this is 70-120 ms for the whole factor.
2. **Panel width 128, panel factorization in one launch per panel step over row blocks**: a grid of (rows/256)
   blocks each holding its 128-column panel slice in shared memory; the pivot search is a two-level fold with a fixed
   partition (block partials written to a (rows/256) array, then a one-block final fold over that fixed-size array,
   which is a "small grid over a fixed count", allowed) and the column scaling and rank-1 update inside the panel run
   per block. That is 2 launches per column (pivot partials, pivot-fin + swap + scale + update) instead of 5, and the
   per-column work touches only the 128-wide panel (not the trailing matrix). Row swaps outside the panel are
   deferred and applied once per panel (`laswp`-style, one launch).
3. **Blocked TRSM** for the panel's U12 block and for the solve: `U12 = L11^-1 A12` as a 128 x 128 triangular
   solve per 128-column tile, one block per tile, fixed in-block order (the dependent chain is 128 long, not n), then
   GEMM for the rest. For `B` (8192 x 64) the two solves become 64 tiles x (triangular tile + GEMM update). This also
   answers `docs/plans/HOST_ROUTE_REMOVAL.md:64` ("blocked device TRSM for many right-hand sides").
4. `lu_factor` returns a resident handle; `lu_solve` takes it (the `IDN_LU_RESIDENT` door already exists,
   `resident.mojo:648-653`): the lu-factor lane stops re-uploading 256 MB.

**(d) Expected.** 64 panels x (128 x 2 column launches + ~4 panel launches) ~ 16.6k launches (80-160 ms) + GEMM
70-120 ms + TRSM tiles (~20-40 ms) + 256 MB upload and 256 MB download inside our clock (~40-60 ms pinned):
0.25-0.4 s against 36 ms kernel-only: ~7-10x, down from 125x. **Bits change** (fold order of the trailing update
and the pivot fold partition); pivot CHOICES do not change unless two candidates tie in |a| after rounding
differences, which the fixed partition rules out across vendors (same bits in, same partials, same argmax).

**(e) Effort.** M-L, strong model (pivot fold under identity, TRSM tile design); the GEMM-entry work is shared with
3.1 and 3.3. **(f) Nothing waits on Modular.** A persistent-kernel LU (one launch, grid-wide barriers) would need a
cooperative-launch / grid-sync primitive Mojo does not expose; record the ask, do not emulate it with spin barriers.

### 3.3 Cholesky (8192 SPD): 1,174 ms (current); torch 12.7 ms

**(a) Today.** `linalg.Cholesky` binds `_mojolearn_gp` (`_cholesky_impl.py:62`) -> `cholesky_factor_poolio`

Classification: unblocked-rate update + serial diagonal chain + host copies.

**(b) Opponent.** cuSOLVER `potrf`: blocked right-looking, `potrf` on a 128-256 diagonal tile (warp-level), `trsm`
for the panel below it, `syrk`/`gemm` on cuBLAS for the trailing update. 12.7 ms for 183 GFLOP = ~14 TFLOP/s.

**(c) Design.** Same shape as 3.2 without pivoting: diagonal tile factor in one block per tile (128 x 128, fixed
in-block order), one blocked TRSM launch for the panel below it (one block per 128-row tile), and the trailing
`A22 -= L21 L21^T` through `identical_gemm` `OP_NT` (full square, or an upper-triangle-only variant later; the GMM
lane already ships "two GEMM blocks over the upper triangle", b512ddf29). Drop the unused pool allocation, replace
the single-thread `copy_f32` with a device-side copy into the output's pinned buffer.

**(d) Expected.** 64 tiles x 3 launches + GEMM 183 GFLOP at 3-5 TFLOP/s (40-60 ms) + 2 x 256 MB copies (40-60 ms):
~0.1-0.15 s, 8-12x torch, from 92x. **Bits change** (trailing fold order). **(e)** M, strong model for the first of
3.2/3.3 (they share the TRSM tile and the GEMM-update pattern; do Cholesky first as the simpler proof, then LU).

## 5. Graph: Louvain, PageRank, connected components (program 3)

Graph: n = 20,000 (`GRAPH_SMALL`, `bench_board_algos.py:123`), k = 10 symmetric kNN (nnz ~ 2-4e5), unweighted; CC
gets the k = 2 CSR. Ours takes a DENSE 1.6 GB n x n adjacency for PageRank and Louvain (the class contract), built
before the clock; cuGraph takes the CSR. All three run on the GPU binding (`bindings/_mojolearn_x_neighbors.mojo:1261,
1265-1266, 1274`), and all three iterate in O(nnz) on a device-built CSR/CSC; the dense input costs a one-time
upload plus O(n^2) setup sweeps, not O(n^2) per iteration.

### 5.1 Louvain: 75,982 ms (taxi) vs cuGraph 146 ms

**(a) Today** (`graph_par.mojo:1199-1367 lv_drive`). `Louvain.fit` runs `graph_symmetry` (uploads the 1.6 GB matrix,
row item uncoalesced, finalizer one thread over n at grid 1: `items.mojo:1438-1468`, `device_ops.mojo:1400-1409`),
then `op_louvain` uploads the 1.6 GB AGAIN (`graph_dev.mojo:142-147`), then three dense one-thread-per-row sweeps
(`LV_ROWCNT` twice, `LV_FILL`, `:541-568`, uncoalesced). ~1-2 s so far. Then per level: Jones-Plassmann colouring
with a fixed hash priority (`:607-622`), rounds in chunks of 8 with a host sync per chunk (`:1274-1283`), a sort by
colour and a readback (`:1290`). Then up to `LV_MAX_SWEEPS = 100` sweeps; per sweep, per colour: one `LV_MOVE` launch
(one thread per node of the colour, in-thread heap sort of its neighbour communities, strict-greater gain so ties go
to the smallest id, `:741-810`), then `_lv_totals` = `SKEY` + `gp_sort` (1 + ~11 merge launches over all nn keys,
`:1062-1081`) + `SFOLD` to rebuild the community degree totals: ~14 launches per colour. Per sweep two readbacks (move
flag, modularity, `:1306, 1178-1186`). Aggregation is sparse (sort over nnzc + per-pair fold, `:889-941`). So with
C colours (a 10-NN graph colours in ~15-30), S sweeps per level and L levels: 14 x C x S x L launches; at
C = 25, S = 30, L = 5 that is ~50k launches plus 300 syncs, which with the sort's small launches (5-20 us each) is
tens of seconds. Classification: launch-volume chain (a sort per colour to recompute totals that could be updated
incrementally), plus two 1.6 GB uploads and three dense sweeps. No FAST branch, no defines.

**(b) Opponent.** cuGraph Louvain (`cpp/src/community/louvain_impl.cuh`, `detail/update_clustering_by_delta_modularity`):
all vertices compute their best move in parallel from CSR with per-vertex `thrust`-style reductions over
neighbours; moves are applied in "up/down" vertex batches to avoid oscillation; community totals are updated by a
sort-by-key + reduce-by-key over the MOVED vertices (not all); aggregation via `coarsen_graph` (sort + segmented
reduce); `max_level = 100`; nondeterministic tie order (its own mismatch note). ~10-20 launches per sweep, no sort
over all nodes per colour.

**(c) Design (identical, deterministic tie-breaks kept).**
1. **CSR entry** (`louvain_csr`): a binding op that fills graph slot `L_G0` (`:1239-1246`) from `indptr/indices` (both
   directions are already stored, `:491-494`), skipping both uploads, `graph_symmetry` and the dense sweeps. The
   Python class accepts `scipy.sparse` CSR (glue only: pointer handoff, as `connected_components._csr_of` does,
   `_expansion_neighbors.py:1867-1879`); the harness hands the CSR it already has (`bench_board_algos.py:2107-2113`).
   Dense input stays supported through the existing path. Bits: unchanged if the CSR's per-row column order equals
   the dense sweep's (ascending), which `_csr_of`'s sorted indices give; assert sorted on the device (a flag), never
   sort in Python.
2. **Incremental community totals in fixed-point integers.** Replace `_lv_totals` (sort + fold per colour) with: each
   moved node of the colour class adds `+deg` to its new community and `-deg` to its old one. Within one colour class
   no two moved nodes are adjacent, but two can move into the same community, so the update is a scatter-add: use
   integer atomics on an int64 (or two-word) fixed-point total (degrees are integers in unweighted graphs; for
   weighted graphs scale weights to a fixed-point integer with the scale a pure function of the input's max weight).
   Integer atomic add is order-independent, so the result is bit-identical on both vendors: this is the REPLACE move
   of IDENTITY_PATHS ("float atomic -> fixed-point integer accumulator"). Launches per colour: 2 (move, totals-apply),
   from 14; and the `gp_sort` over all nn keys per colour disappears.
3. **Fewer syncs**: compute the per-sweep move flag and modularity in one launch after the colour loop (already
   device-side), read both back once per sweep (one sync instead of two), and run the colouring's 8-round chunks as
   16-round chunks with the convergence flag read once (the colour count is bounded by max degree + 1 = 11 for a 10-NN
   graph, so 2 chunks suffice; a rule from the degree bound, not the dataset).
4. Keep the pinned move order (DEVIATION 5204) and the strict-greater gain rule exactly; record the colour count in
   `n_colours_` for the next read.

**(d) Expected.** 2 x C x S x L launches ~ 7k at C = 25, S = 30, L = 5, plus ~150 syncs: ~0.2-0.5 s of launch floor
+ aggregation sorts (~50-100 ms) + no uploads: ~0.5-1.0 s vs 146 ms, i.e. 3-7x from 520x. **Bits**: the CSR entry
is bit-neutral; the integer totals change the float path's bits (the totals today are float folds) and are then
exactly reproducible; the move decisions can change where a float total previously rounded. Change NV, AMD and the
host twin (`x_neighbors/graph_host.mojo`) together. **(e)** M, strong model (fixed-point scaling rule for weighted
graphs, identity of the modularity gain under integer totals). **(f)** A single persistent kernel per sweep would
need grid sync (not in Mojo); not required.

### 5.2 PageRank: 1,377 ms vs cuGraph 4.7 ms

**(a) Today** (`graph_par.mojo:1098-1175 pr_drive`): the 1.6 GB upload (`graph_dev.mojo:131-139`), four O(n^2)
dense setup sweeps (`PR_COLCNT` twice at `:1115, 1136`; `_pr_colfill`; `_pr_rowsum` uncoalesced, `:366-415`) on 157
blocks, then a CSR iteration of 5 launches + one residual readback with a host sync per iteration (`:1147-1172`,
`:1164`). The iteration is O(nnz) and cheap; the 1.4 s is the upload (~150 ms pinned, more pageable), the dense
sweeps on 20,000 threads (each reading 20,000 cells: 1.6 GB x 4 at poor coalescing, ~hundreds of ms), buffer
allocation (each `alloc` syncs, `graph_dev.mojo:60-70`) and the two separate `p2m_fill` binding calls before it
(`_expansion_neighbors.py:1763`). Classification: host-to-device copy + O(n^2) setup, not the algorithm.

**(b) Opponent.** cuGraph `pagerank_impl.cuh`: CSR SpMV per iteration (`per_v_transform_reduce_incoming_e`), a
dangling-sum reduction, an L1 residual with the convergence test on the device every iteration (one readback);
100 iterations max, tol 1e-6. 4.7 ms ~ 30-60 iterations x a few SpMV launches at 20k nodes.

**(c) Design.** CSR entry filling `P_CNT/P_ROWS/P_VALS` directly (`:1123-1126`), fold the two `p2m_fill` calls into
the op, allocate the iteration buffers once per call without per-allocation syncs, and read the residual back every
iteration but without the extra `GP_FFIN` fold launch (one launch computes the step and its L1 partials with a fixed
partition; one small fold). Bits: unchanged (same CSC order, same fold shape) if the per-column order stays
ascending; if `C43_RESIDENT_NORMALIZATION` is adopted at the same time, bits change once. **(d)** ~5 launches x ~50
iterations + 50 syncs: ~5-10 ms, 1-2x cuGraph from 290x. **(e)** S, Opus.

### 5.3 Connected components: 1,117 ms vs 13 ms

**(a) Today.** Already CSR (`_cc_csr_device`, `iter_device.mojo:466-533`): hook-and-compress with an atomic min,
O(nnz) per round; the cost is a per-call pinned host buffer (`:474-475`), three uploads, a 4-byte readback with
`synchronize` per round (`:520-527`), three separate binding ops (`_p2m_iota`, `cc_iterate_csr`, `_p2m_relabel`,
`_expansion_neighbors.py:1810-1826`) and Python int32 casts. The code's own note says the Apple time was "overhead,
not kernels" (`:539-546`). The board figure may predate the CSR switch (2026-10-01, `:1807`).

**(c) Design.** Promote the FAST + Apple batching (`CC_FAST`: 4 rounds per readback, device relabel,
`:538-579`) to IDENTICAL on NV and AMD: hook (atomic min) and jump are order-independent, so batching rounds does
not move bits; relabel on the device; one binding op; a pooled pinned buffer. `C33_FROZEN_CHUNKS` (`graph_controls.mojo:71-72`)
is the same idea but marked NOT COMPILED (`iter_device.mojo:448`): delete it or finish it, not both. **(d)** ~20
launches + 5 syncs: ~3-5 ms, from 84x to 1.5-3x. **(e)** S, Opus. **Bits unchanged.**

## 7. TSQR family: qr, svd, lstsq (program 5): untimed on HEAD

**(a) Today** (`read_tall_skinny.md`). The 27-55 s rows are per-column Householder with one-thread norm folds and a
Python sign-flip loop; gone. HEAD: `ts_factor_device` (`tsqr_device.mojo:662-748`) with 2048-row leaves, 16-column
panels, arity-2 tree: istella 14 panels x (`ts_leaf_panel_kernel` grid 488 + `ts_leaf_update_kernel` grid 488 x nch)
+ ~9 `ts_combine` + one sync; apply (`_ts_apply_dcb`, `:808-868`) ~24 launches + one sync. The remaining serial pieces:
`ts_combine_kernel` is one threadgroup per pair with every thread recomputing the norm chain and column threads looping
i <= j (`:438-474`; the top tree levels run on one SM); `ts_capply_kernel` is one thread per column serial over all n
reflectors (`:497-511`); inside the panel kernel the norm uses 16 of 256 lanes unless fused, reflectors are applied
one at a time with barriers, T is 15 serial passes (`:255-358`). The trailing matrix is re-read per panel (14 x 0.9 GB
each way in factor and apply: tens of ms). The small 220 x 220 SVD of R is round-robin Jacobi at 219 launches per
sweep, up to 60 sweeps, one sync per sweep (`device.mojo:3570-3630`; `rr_svd.mojo:25`): launch-bound, ~10 ms per sweep.
Our whole clock includes the 880 MB upload and the 880 MB Q (or U) download; torch/cupy are kernel-only.

**(b) Opponent.** torch `linalg.qr` = cuSOLVER `geqrf` + `orgqr` (blocked Householder, `larft`/`larfb` compact-WY
with cuBLAS GEMM trailing updates, 32-128 column panels); cupy `svd` of 1M x 220 = `gesvd` (tall case: `geqrf` first,
then bidiagonalization + QR iteration on the 220 x 220 R, then `orgqr`-shaped back-multiplication). 228-243 ms.

**(c) Design.** Measure first (Step 0 with `MOJOLEARN_LINALG_TIMING=1`). Then, in order of likely payoff:
1. **Panel trailing update as a GEMM** (compact WY): per 16- or 32-column panel compute `W = Y T` once and apply
   `A_trail -= Y (T^T (Y^T A_trail))` as two `identical_gemm` calls per leaf block (batched over the 488 leaves with
   the strided entry) instead of the per-reflector in-kernel update. Bits change (fold order of the update). Cuts
   the 14 trailing sweeps' arithmetic to GEMM rate; the traffic stays 2 passes per panel unless panels widen to 32-64
   (a size rule: panel = min(d, 64)).
2. **Parallel combine**: the pairwise R-combine (`ts_combine_kernel`) as a 2d x d Householder QR with one block per
   pair but with lane-parallel norms (fixed 2-level fold) and column-parallel reflector application; the top levels
   are few and tiny (9 levels of <= 244 pairs), so this is ~10 launches of small work; the serial norm recompute per
   thread is the waste to remove.
3. **Apply tree**: `ts_capply_kernel` as a block-per-column-tile kernel with the reflectors staged in shared memory
   (n = 220 reflectors x 2d rows), not one thread per column over all n.
4. **Small SVD of R**: keep the identical round-robin Jacobi but run all 219 rotation sets of a sweep in ONE launch
   with a fixed in-launch order per block (each round's 110 rotations are independent; successive rounds depend on
   the previous, so a round-robin schedule inside one launch needs the whole 220 x 220 matrix in shared memory
   (194 KB fp32: too big for a 48 KB default; use 128 x 128 sub-blocks, i.e. block Jacobi on R) or 2 launches per
   round without the per-sweep sync (read the off-norm back every 4 sweeps). The honest small win is the sync
   removal: 60 syncs -> 15.
5. **Clock**: Q/U download pinned; the upload is the board's rule and stays inside the clock, recorded as the copy
   field.

**(d) Expected.** qr/svd istella: 3-4 passes over 880 MB (~5-8 ms) + GEMM-rate updates (14 panels x 2 x 1M x 220 x
16 flops ~ 100 GFLOP, 30-50 ms) + small SVD ~50-100 ms + 880 MB up and down (~70-100 ms pinned): ~0.2-0.3 s whole
against 228-243 ms kernel-only: parity-ish, ratio ~1-1.5x. If Step 0 shows HEAD already near 0.5-1 s the whole program
is M for ~3x; if it shows seconds, item 1 is the cause. **(e)** M, strong model (WY fold order under identity).
**(f)** Nothing waits on Modular.

## 8. MoE, conv2d, resnet-block GEMMs (program 6)

fused with the ReLU/add epilogues (one launch per block instead of 6).

**(d) Expected.** MoE 29-34 -> ~8-12 ms (~3x torch from 9x); conv 9.5 -> ~3-4 ms; resnet 20.7 -> ~6-8 ms (~10x
torch from 30x). **The floor is structural**: IDENTICAL forbids TF32 (contract :165) and NVIDIA has no exact-fp32
matrix unit, so fp32 CUDA cores (~90 TFLOP/s peak, 20-40 practical) against TF32 tensor cores (~360 TFLOP/s) leaves
~5-10x on conv-shaped work. A 3xTF32 split-product emulation would be a new IDENTITY_PATHS decision (its rounding
differs from the fma chain) and is out of scope here. **(e)** M, strong model. **(f)** Nothing waits on Modular.

## 11. Smaller family members

- **knn-imputer** (2,331 ms vs 23): brute-force nan-euclidean with one thread per missing cell scanning all m fit
  rows x d serially (`x_neighbors/iter_device.mojo:1236-1299`), distances recomputed per missing cell of the same row.
  Design: one distance pass per QUERY ROW (not per cell) as a tiled pinned-distance kernel (the `pinned_distance_tile`
  family exists), masked over the row's missing pattern, then a fixed-order top-k per row. ~10x. M, Opus. Bits change
  (fold order).
- **ivf-pq** (785 vs 11.7 ms search): coarse step one thread per (query, list) serial over 220 dims
  (`x_ann/ivf_scan_device.mojo:63-69`): a GEMM or the pinned distance tile; the resident handle of Section 6. M, Opus.
- **cholesky**: Section 3.3.

## 12. What must wait for Mojo/Modular, and what does not

Nothing in programs 1-9 depends on an unsupported toolchain feature. Three things would help and are not available;
record them as asks and do not emulate them:
1. **Grid-wide synchronization / cooperative launch** (persistent-kernel Jacobi, LU, Louvain sweeps). Spin barriers on
   global atomics are a workaround and are not to be built.
2. **Device-side launch graphs** (CUDA Graphs / HIP graphs) to cut the per-launch floor that dominates eigh, LU,
   Louvain and the small Jacobi; until then the plan reduces launch counts algorithmically.
3. **An exact-fp32 matrix-unit path on NVIDIA**: none exists in hardware; a 3xTF32 emulation is possible in Mojo today
   but is a numeric-contract decision (IDENTITY_PATHS), not a toolchain wait.
There is no cuSOLVER/cuBLAS/cuSPARSE/cuDNN binding in Mojo's public surface and the repo would not use one under
IDENTICAL anyway (closed vendor libraries pick per-vendor fold orders); the identical GEMM is the substitute and is
already at parity with torch bf16 on the board's GEMM row.

## 13. Lane split and order

1. **G0 (Opus, no code): re-race** the 25 stale cells on nv and amd with stage timers (Section 0 lines). Replace the
   board rows through the board tools; attach provenance (wheel, commit).
2. **G2 (Opus): device I/O** for optimizers, embedding, batchnorm2d/dropout2d/layernorm, maxpool pool cap, MoE x;
   `graphsage/gcn` single-sync fit. 11 cells, bits unchanged, each its own define per the experiment rules.
3. **G3a (Opus): PageRank CSR entry + CC batching; G3b (strong): Louvain CSR entry + fixed-point totals.**
4. **G4 (Opus): IVF resident handle + deterministic trainset + lazy shift on NV/AMD**, recall gate.
5. **G1 (strong): identical GEMM strided/accumulate entry -> Cholesky blocked -> LU blocked -> eigh tridiagonal
   promotion.** One lane, in that order; each step is its own define and A/B.
6. **G5 (strong): TSQR WY trailing update + parallel combine + small-SVD sync removal**, only after G0's numbers.
7. **G6 (strong): MoE grouped GEMM; implicit conv.**
8. **G7, G8 (Opus): tree-shap single upload/table cache; NB 64-bit counts.**

Every change: a `-D MOJOLEARN_<AREA>_FAST_<NAME>`-style define (IDENTICAL ones under `MOJOLEARN_IDN_*`), default off
until the A/B on nv and amd (average of the two ratios, Andrew 2026-10-08), identity by the stored output hash on
both vendors, a row in `docs/apple-fast/EXPERIMENTS.md`, losers deleted before merge. No dimension rules: every
threshold above is written as a function of n, d, degree bound or device memory, never of a board shape.
