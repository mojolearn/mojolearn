# Test migration plan: Python tests to Mojo checks (2026-11-14)

Andrew, 2026-11-14: move the Python test files to Mojo with Opus lanes. This file is the inventory and the plan
those lanes execute. It binds with AGENTS.md "Move native correctness tests to Mojo (Andrew, 2026-11-10)", "The
verify command is protected (Andrew, 2026-11-11)" and "remove what a change made unnecessary".

Scope: every `test_*.py` under `python/mojolearn/tests/` (671 files) and `tests/` (5 files plus 3 under
`tests/tools/`): 679 files, 120,856 lines at `origin/preinteg/wave2-20261113` (`8ab734d820`). Nothing was compiled or
run to write this plan.

## Classes

- **NATIVE** (moves to Mojo): kernel numerics, algorithm correctness against a reference the test computes, native
  state and lifetime, device buffers, fold order, identity hashes the test computes, optimizer and training-step math.
- **BOUNDARY** (stays Python): the Python API surface: argument admission, exceptions and messages, returned object
  types, NumPy/pandas/torch buffer admission, refused callbacks, save/load and pickling through Python, scikit-learn
  compatibility, framework adapters, import behaviour. Source-text tests (they read repository files and run no
  product call) are counted here with a `source-text` mark.
- **VERIFY** (stays, protected): the tests of `python -m mojolearn verify` (`test_verify_*`, `test_verification_*`,
  `test_host_only_verifier.py`) and the release tooling tests under `tests/tools/`. `verify` itself imports no test
  module (checked: no `mojolearn.tests` import in `python/mojolearn/_verify*.py`, `_verification*.py` or
  `verify_reference/`), so no NATIVE port can break it. Some NATIVE/MIXED files import helpers FROM verify
  (`_verify_native_runtime.audit_native_call` in 276 places, `_verify_all`, `_verify_model`, `_verify_causal_lm`):
  a port drops the import from the deleted Python; it never moves or edits the verify module.
- **ORACLE** (stays as a testing tool): the reference is an independent external library (scikit-learn, SciPy,
  torch). The table says whether the oracle's output can become a stored fixture so that the check moves.
- **MIXED**: both. The NATIVE functions are named per file; they move, the rest stays.

## Method and its accuracy

`~/mojolearn-evidence/briefs-20261114/test-migration-inventory/classify.py` parses every file (one file per worker,
`multiprocessing`, workers = cores) and classifies every test function (`test_*`, the `arm_*` functions of the
script-style gates, and every top-level function of the 7 gates driven only by `main()`) from its own source:
numeric assertions and in-suite reference helpers (`_fold_reference`, `_lr_reference`, `_mamba_block_reference`, ...)
count as NATIVE; `pytest.raises`, `monkeypatch`/`tmp_path` fixtures, pickling, save/load, dtype and type checks,
hooks and callbacks count as BOUNDARY; an external-library name in a function with a numeric assertion is ORACLE;
reading repository files with no numeric assertion is source-text. A file is NATIVE only when every function is
NATIVE and its name carries no boundary word; ORACLE or BOUNDARY when NATIVE functions hold under a quarter of its
lines; MIXED otherwise. `build_plan.py` then applies, in order, the 51 earlier per-file decisions of
`docs/plans/native_test_migration/inventory.tsv` (retain-python-boundary, split-migrated, split-needed, ...) and 42
hand decisions (40 spot checks across every class, recorded in `overrides.tsv` beside the script, plus two reviews).
The spot checks agreed with the final heuristic on 32 of 40 (the heuristic was tuned on that sample, so read the
figure as an upper bound). Every miss was the heuristic calling a boundary file MIXED, or one repeat-bits file
BOUNDARY; it never called a boundary-only file NATIVE in the final run. **So every lane starts by reading each of its
MIXED files and confirming the native function list before it ports anything; a file that turns out to be all
boundary is left alone and reported.**

## Model check

`checks/native_tests/spectral_prediction_*` (commit `776be47afa`, ported from `test_spectral_predict.py`):

- `spectral_prediction_cases.mojo`: the original fixtures (inputs, options, expected relations) and helpers; no
  `main()`, importable.
- `spectral_prediction_cpu_suite.mojo` / `spectral_prediction_gpu_suite.mojo`: `run_checks()`. The CPU suite runs its
  independent fixtures across host cores with `core.host_parallel.host_parallelize` and a private failure slot per
  fixture; the GPU suite runs fixtures in order on the device, kernels keep their own parallelism.
- `spectral_prediction_cpu.mojo` / `spectral_prediction_gpu.mojo`: only `def main() raises: run_checks()` (AGENTS.md:
  a module with `main()` cannot be imported as a package).
- pixi tasks `check-native-spectral-prediction-cpu` (`-D MOJOLEARN_NUMERIC_IDENTICAL=1 -D MOJOLEARN_COLUMN_CPU=1`) and
  `check-native-spectral-prediction-gpu` (`-D MOJOLEARN_NUMERIC_IDENTICAL=1`).

The brief's name form `checks/<family>_<topic>_check.mojo` is replaced by this live convention under
`checks/native_tests/` (578 files already there), so the new checks sit beside the earlier ports.

## What every lane does

1. Branch `lane/<lane>` from the integration branch the orchestrator names; worktree `~/mojolearn-wt/<lane>`. No
   compile, no tests, no boxes (AGENTS.md "Lanes"). Load the `mojo-skills:mojo-syntax` skill; follow "Mojo rules that
   cost a build round" exactly.
2. Read each file of the lane. For MIXED files confirm the native function list in the per-file table.
3. Write the suite, cases and `main()` wrappers for each check and add the pixi tasks (`check-native-<stem>-cpu`,
   `-gpu` when the file ran on a device). Independent fixtures run across host cores (`host_parallelize`), never in a
   serial loop (hard rule "write code to run in parallel"); a GPU suite says in its docstring why its fixtures run in
   order on one device.
4. Call the family's Mojo entry (table below), never the Python binding. Keep the test's inputs, options, tolerances
   and assertions; never weaken one. Fixtures: seeded data regenerated in Mojo when the generator is ours; when the
   test depends on NumPy's PCG64 stream or an external oracle, store the bytes as `.npz`/raw under
   `checks/fixtures/<family>/` with the generating script in `tools/`, and say so.
5. Delete what moved: a NATIVE file is deleted; from a MIXED file the native functions (and imports, fixtures and
   parametrizations only they used) are deleted. Update every pixi task, tool and CI line that names a deleted file or
   function (`Ext` column). A helper under `python/mojolearn/tests/_*.py` whose last user leaves is deleted in the same
   lane (helper table).
6. Never touch anything `python -m mojolearn verify` imports; the report says verify was not touched.
7. Bits: none change (tests only). Report: branch/head, files deleted or shrunk, checks written, pixi tasks added,
   fixtures stored, helpers removed, every MIXED file whose list changed, units the integrator must build (the check
   modules only; no binding).

## The three hardest files

1. `test_linalg_identity.py` (1,320 lines, `classical` lane, script-style gate run by a pixi task): the identity gate
   for `mojolearn.identical.gemm.fp32.v1` compares every execution plan and orientation word for word against
   `gemm/host/gemm_oracle.mojo::gemm_oracle` through the Python path. The bit comparisons move (they are the point of
   the file); the marshalling and refusal arms stay. Splitting a single `main()`-driven report into a Mojo suite and a
   smaller Python gate, and keeping the pixi task and the DEVIATION references consistent, is the largest single job.
2. `test_arima_surface.py` (1,027 lines, `msel-metrics-tsa-2`, script-style, named by pixi and five tools): its own
   docstring says the arithmetic is gated in `arima/checks/*.mojo` and this file gates the Python path, yet its
   planted-parameter recovery, forecast and batch-invariance arms compute independent references. The lane must
   decide arm by arm which already exist in `arima/checks/` (delete them here, no new check) and which are new
   (port them), and keep the marshalling/refusal arms in Python.
3. `test_svr_surface.py` (871 lines, `classical`): the same surface-gate shape over SVR with fixtures, solver results
   and refusals interleaved in one report; earlier SVR ports (`docs/plans/SVR_NATIVE_HANDOFF_20261111.md`,
   `checks/native_tests/svr_native_*`) already cover part of it, so the lane must map each arm to an existing
   check before writing a new one.

## Open points for the orchestrator

- The classification is heuristic plus 42 hand decisions; lanes confirm MIXED lists and report changes. A lane that
  finds a NATIVE function already covered by an existing `checks/native_tests/` suite deletes the Python function
  and writes no new check.
- 16 files are `split-migrated` in the earlier inventory: their native part is already in `checks/native_tests/`,
  but the Python numerical cases were kept "until acceptance". Their lane deletes those Python cases.
- The 24 ORACLE files (22 scikit-learn/SciPy, 2 torch-adapter) stay. Converting the scikit-learn outputs to stored
  fixtures would move about 2,800 more lines; that is a separate decision, not part of these lanes.
- New checks are not run by anyone until the orchestrator's integration compile; the Python test is deleted in the
  same lane, so between the merge and the first run of the check that coverage exists only in source. The
  orchestrator runs the new `check-native-*` tasks with the next integration build.
