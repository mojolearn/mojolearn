# Vendor primitives: what the MAX toolchain ships, and what it answers correctly

**Scope.** This file is the TOOLCHAIN INVENTORY for the whole tree — what MAX
ships, what it does not, and which of the shipped calls have been RUN and
judged — plus the call-site audit for the cuVS / cuML / RAFT sections
(`cluster/`, `neighbors/`, `decomposition/`, `dbscan/`, `glm/`).
`VENDOR_LIBS.md` is the CatBoost boosting-side call-site audit and does not
repeat the inventory.

**The rule that governs both files is `PORTING_RULES.md` 0b-i, FOLLOW THEIR
DISPATCH**, which replaced "where the incumbent calls a vendor primitive, call
OURS" on 2026-08-19. Read it there; it is not restated here. The consequence
for this file: **an available primitive is not a reason to substitute.** Before
citing any row below, answer in writing whether their dispatch takes this path
for these parameters and whether the step is standalone in THEIR code too. If
either answer is no, port their kernel.

Everything above Appendix A is **probed against this toolchain**, not read from
documentation. `AVAILABLE` means the import compiled, and nothing more.

# THE STANDING RULE: A SIGNATURE PROVES REACH, A RUN PROVES THE ANSWER

**A signature check proves the GPU is REACHABLE. Only a run against an
independent oracle proves the answer is RIGHT. Nothing in this file may be
cited as a reason to use a primitive unless the correctness table below gives
it a verdict, and the only verdict that permits use is `GPU, CORRECT`.**

This is not a general principle. It is the specific thing that went wrong.
`nn.argsort.argsort` was listed here as **GPU** because it takes a `ctx` and a
`target`. It does take both, it runs on the device, it raises nothing, and it
returns a well-formed permutation that is **not sorted** above 256 elements.
It was one edit away from being substituted into the ball-cover index build,
which would have shipped a DBSCAN that silently drops real neighbours. It was
caught only because a check asserted an INDEX INVARIANT — that each landmark
group is ordered — rather than a final answer.

Three separate times an import path has been read as evidence in this
repository and been wrong: twice a MISSING path was read as missing silicon
(float `atomicAdd` on Metal works; warp shuffles work and live under
`std.gpu.primitives.warp` and `std.gpu.primitives.id`), and once a path that
resolves and lies.

So the tiers are:

    NOT FOUND       the symbol does not exist, or the capability is refused
                    at compile time
    CPU ONLY        it exists, and neither a `ctx` nor a `target` is in the
                    signature
    GPU, UNCHECKED  it reaches the device and no run has judged its answer.
                    NOT a reason to use it.
    GPU, CORRECT    it ran on the device and matched an INDEPENDENT host
                    oracle, on a scattered hashed fixture, at sizes that
                    straddle the block width
    GPU, WRONG      it ran and did not match

**How a `GPU, CORRECT` verdict is earned**, because a weak check is worse than
none:

- the oracle is computed **independently on the host**, never by rearranging
  the output of the same call;
- the fixture is **scattered and hashed** (splitmix64 over `(index, salt)`).
  A fixture that is uniform, sorted, or affine in the index verifies a total
  and nothing about placement, and that exact mistake has passed a wrong
  reduction here twice;
- the sizes **straddle the block**: 1, 2, 255, 256, 257, 512, 513, 1023, 1024,
  1025, 4096 and 100003. The `argsort` bug is invisible at 256 and at every
  size below it, and 100003 is prime so no tile count divides it evenly;
- selection primitives compare **values strictly** and indices **only up to
  ties**.

## The `n = 1` defect, and the five call sites that reach it

`core/gemm.mojo::gemm_nt` is `linalg.matmul.matmul[transpose_b=True]` and
nothing else. At `n = 1` it leaves 63 of 64 output rows **untouched** — not
zeroed, untouched, so a caller reusing a buffer reads stale data and a caller
with a fresh one reads whatever the allocator left. **`gemm_nt` routes `n = 1`
to `gemv_n` now**, which is what RAFT does there too, and the wired row in the
correctness table proves the guard through the real wrapper. The sites are
recorded because `n` is a user-facing count at every one of them:

    cluster/impl/cluster/detail/min_cluster_distance_compute.mojo:197
        nc = min(centroid_batch, n_clusters - c_idx), so this is n = 1
        whenever n_clusters is 1 OR n_clusters % centroid_batch == 1.
        That is not an exotic input; it is a remainder.
    glm/impl/linalg/detail/lstsq.mojo:120 and :193
        gemm_tn(..., n_cols, n_cols, n_rows) -- and gemm_tn ends in gemm_nt.
        Simple linear regression on ONE predictor is n = 1.
    decomposition/impl/linalg/detail/pca.mojo:202
    decomposition/impl/linalg/detail/tsvd.mojo:89
        same shape, n_cols again.
    neighbors/impl/neighbors/detail/knn_brute_force.mojo:154
        n_index = 1.

## FAST products on NVIDIA are TF32, 2026-08-23 (DEVIATIONS 529, 540)

The correctness table above is an Apple M4 measurement, and its two
`linalg.matmul` rows say **GPU, CORRECT** against a Float64 oracle at an fp32
budget. On the H100 leg of E2 the same products failed that budget under FAST:
`checks/gram_splitk_check.mojo::check_gram_vendor_arm` at 33x33x257 by
2.4e-5 of the magnitude, and the k-means unfused assignment arm
(`cluster/checks/kmeans_check.mojo::check_assignment_arm_dispatch`) by 4e-5
-- both ~100x outside fp32 and well inside TF32. Both are `core/gemm.mojo::
gemm_nt` = `linalg.matmul`. Read from the pinned toolchain's source (tag
`max/v26.5.0`):

- `linalg/matmul/__init__.mojo:59,90`: `use_tf32: Bool = True` -- "allow TF32
  tensor-core truncation for fp32 inputs" -- is the DEFAULT.
- `linalg/matmul/gpu/__init__.mojo:493-498`: `use_tf32=False` is a
  COMPILE-TIME ASSERT except on SM100 (Blackwell): "use_tf32=False is only
  implemented for the SM100 matmul dispatch". On an H100 there is no flag.
- `linalg/matmul/vendor/matmul.mojo:73,116`: the cuBLAS fallback hard-codes
  `vendor_matmul[use_tf32=True]`, which is `COMPUTE_32F_FAST_TF32` plus
  `CUBLAS_TF32_TENSOR_OP_MATH` (`vendor/blas.mojo:751-758`, with the source's
  own comment "the result is not bit-wise identical to the result of FP32").
- AMD CDNA's fp32 MFMA is the full-precision `16x16x4` f32 instruction
  (`layout/tensor_core.mojo:1446`) and its rocBLAS fallback runs at compute
  type fp32 (`vendor/blas.mojo:929`): **fp32**. Apple M1-M4
  (`gemm_kernel_apple_8x8`): **fp32**. Apple M5: the fp19 simdgroup MMA path
  is ON BY DEFAULT (`MODULAR_APPLE_M5_ALLOW_LOSSY_F32_MATMUL` defaults to "1",
  `utils_gpu.mojo:564-569`), so an M5 is TF32-class unless that variable is
  "0" -- transcribed, untested on an M5.

So the rows above are **GPU, CORRECT AT FP32 ON APPLE M1-M4 AND AMD CDNA,
TF32-ACCURACY ON NVIDIA** under FAST. The property is a KERNEL MATRIX row
(`checks/kernel_matrix.mojo::column_vendor_fp32_matmul_is_tf32` /
`vendor_fp32_matmul_is_lossy`, the latter folding in the M5 generation at
runtime), read by both checks, which hold a vendor product to
`VENDOR_TF32_PRODUCT_REL_BOUND` (1e-3 of the magnitude: 2^-10, a product of
two operands each rounded to 10 mantissa bits) on a lossy column and to the
fp32 budget everywhere else, and print which. Each check also carries a
self-sabotage that rounds the operands to TF32 on the host and proves, on
the Mac, that the fp32 budget rejects the result and the TF32 bound admits
it -- the two tolerances separate the classes without a tensor core.

WHAT THIS MEANS FOR THE ESTIMATORS, FAST MODE, NVIDIA COLUMN ONLY: every
product through `gemm_nt` / `gemm_tn`'s vendor arm is TF32-accuracy --
PCA / truncated SVD / OLS's Gram product (at EVERY shape on NVIDIA, because
the split-K kernel is the Apple column's arm), PCA transform and inverse
transform, OLS step 5, k-NN brute-force distances, k-means++ candidate costs.
The k-means Lloyd ASSIGNMENT is not: the shipped arm is the fused SIMT kernel
(fp32), which is why the fused arm was RIGHT on the H100 and the diff against
the vendor arm was what failed. `gemv_gpu` (OLS step 6, predict) is a CUDA-core
kernel and is not on this list. **Under IDENTICAL none of it is reachable**:
`gemm_nt` is `pinned_gemm_nt_kernel`, `gemm_tn` is the split-K kernel or a
refusal (DEVIATIONS 521, 526), and the E2 IDENTICAL cards matched Apple stage
for stage on the H100 the same day.

ONE MORE THING THE COLUMN SIMS FOUND: the flat fp32 budget (1e-5 of the
magnitude, calibrated at k=10007) is ALSO too tight for a closed fp32
product at k=100003 -- the `-D MOJOLEARN_COLUMN_AMD` build forces
`check_gram_dispatch`'s 32x32x100003 wrapper call onto Apple's own fp32
`gemm_kernel_apple_8x8` and it lands 1.3e-5, no tensor core involved, a
serial fold at k=1e5 being wider than one at 1e4. A closed product (order
unknown) now earns `4 x 2^-24 x sqrt(k)` on top of the flat budget on every
column (`VENDOR_SERIAL_FOLD_REL_PER_SQRT_K`); our split-K kernel keeps the
flat budget. A real MI300X under FAST would have failed at exactly that
line.

NOT CHANGED: no vendor call was replaced and no tolerance was loosened on an
exact column beyond that k-scaled fp32 allowance. Forcing fp32 through MAX is not available on the H100 (the
assert above); a hand-written fp32 N-T product for FAST would be the
closed-library exception arguing against the vendor rule on accuracy rather
than throughput, and that is a decision for the lane that owns `core/gemm.mojo`,
priced (a 3xTF32 emulation costs ~3x the tensor-core time; the fp32 SIMT path
costs more). `check_pinned_gemm_is_batch_invariant`'s H100 REPORT the same day
(n=64 differs from n=4 in 234 of 256 cells) is the same kernel seen from the
launch-invariance side.

## Two hardware claims this repository made for a month, both FALSE

**Mojo HAS warp primitives.** This repository has claimed since its first
commit that it does not, in `PORTING.md 2`, `PORTING.md 8`, in the reasoning
that made RAFT's `select_warpsort.cuh` "untranslatable", and in the memory
notes. That claim was wrong. The namespace is `std.gpu.primitives.warp`, and
the earlier searches looked under `std.gpu`, `max.gpu`, `std.gpu.block` and
`max.gpu.block`, all of which miss the `primitives` level.

    AVAILABLE  std.gpu.primitives.warp   shuffle_down, shuffle_idx,
                                         shuffle_xor, lane_id, prefix_sum,
                                         reduce, sum, max, broadcast
    AVAILABLE  max.gpu.sync              syncwarp
    AVAILABLE  max.gpu.primitives.block  sum, max, min, broadcast, prefix_sum

What follows from it has to be re-derived rather than assumed:

- `cub::WarpScan` and `cub::ShuffleIndex` in `histogram_utils.cu`, which
  `PORTING.md 8` replaced with a block scan and called a fidelity loss, may
  now be portable directly.
- RAFT's `select_warpsort.cuh` was ruled out at 14 warp intrinsics on the
  same false premise, and under the rule change at the top of this file it is
  now the file that MATTERS. cuVS's dispatch for a normal k does not call
  `select_k` standalone at all: `knn_brute_force.cuh:443` goes to
  `fusedL2Knn`, whose selection is a register-resident
  `faiss_select::WarpSelect` queue inside the distance kernel, and
  `select_warpsort.cuh` is the port of that family. Finishing it is the work;
  the three `set_k_th_` queues in `neighbors/NOT_IMPLEMENTED.tsv` are what is left.

**A float `atomicAdd` DOES work on Metal.** Probed on this M4: 1024 threads
each adding 1.0 return exactly 1024.0. This file previously called it a
hardware limit; that was wrong, and every design in this tree that cited it
has to be re-argued on its own merits. `checks/fixed_point.mojo` survives
the re-argument, but on a different ground: an integer accumulator is exactly
order-independent and a float atomic is not, so fixed point is what makes a
fit reproducible run to run and device to device. It is a CHOICE about
determinism, not a workaround for missing hardware.

## Accepting a `DeviceContext` is not the same as dispatching on it

Three calls resolve, typecheck, and fail at a level the signature does not
advertise: `matmul` with `transpose_a` (compile-time constraint), `matmul
[transpose_b]` at `n = 1` (writes nothing), and `linalg.transpose` on device
buffers (aborts the process). All three carry their evidence in the
correctness table above.

The third one killed the planned unblock for PCA and OLS. The identity was
right (`Xt . Xt^T == X^T X` turns the unsupported T-N shape into the supported
N-T one), it compiled, and it died on execution. `linalg.transpose` takes an
`Optional[DeviceContext]`, and **accepting one is not the same as dispatching
on it.** That sentence applies to every row anywhere in this file whose "GPU"
reading rests on an `Optional[DeviceContext]` rather than a required one.

**How the T-N Gram shape is served instead.** RAFT's `ColKernelPolicy`
(`raft/linalg/contractions.cuh:96`) was ported into `covariance_kernel` and
then DELETED when it measured ~15 GFLOP/s against `linalg.matmul`'s ~248. Today
`core/gemm.mojo::gemm_tn` is a dispatcher: tile-starved outputs (m = n <= 128)
go to the hand-written split-K Gram kernel `core/gram_splitk.mojo`, because the
tuned matmul measured ~25 GFLOP/s at 32x32x4M — a 32x32 output is ONE tile of
parallelism; larger outputs go to `gemm_tn_via_transpose`, which materializes
the transpose with `column_stats.mojo::transpose_kernel` and then calls the
tuned N-T matmul. **`transpose_a` is why PCA and OLS did not move across six
benchmark rounds**, and it will not arrive by upgrade: the parameter's own
published description reads "currently unsupported" and
`linalg.bmm.batched_matmul` carries the identical "not yet supported", so it is
a documented product limit across the whole matmul family, not a local quirk.
`transpose_b` is supported everywhere, including `gemv_gpu`. No future round
should re-plan around `transpose_a` arriving. The ZERO-COPY `col_major`
view was probed as a third route on 2026-08-19 (LANE covariance-unblock) and is
**UNWIREABLE**: matmul's stride handling is arm-dependent (correctness table).
It produced a bit-identical Gram matrix where it worked and a non-symmetric
wrong one at PCA's and OLS's own check shapes, caught by
`check_covariance_is_symmetric` and the Jacobi convergence gate on the first
run.

## Built out of a block primitive because the device-wide one is missing

`cub::DeviceScan::InclusiveSum` has no shipped GPU counterpart. `nn.cumsum`
carries neither `ctx` nor `target` and is CPU-only.

So `cluster/checks/plus_plus.mojo` builds one from
`max.gpu.primitives.block.prefix_sum` in three stages: chunk sums, an
exclusive scan of the chunk totals, then an inclusive scan within each chunk
plus its offset. `check_device_inclusive_scan` verifies it against a host
scan at 20,000 elements and it is EXACT.

That is the pattern for every missing device-wide primitive on this list:
the block-scope one ships, and two extra launches turn it into the
device-scope one. It is worth writing down because the alternative that keeps
suggesting itself, a fixed per-thread slice, silently caps the kernel at
`threads * slice` and truncates without raising. That bug shipped once in
DBSCAN's CSR and was found by audit, not by a test.

## How to add a row

Three steps, and the third is not optional.

1. Probe the import. Record AVAILABLE or NOT FOUND **with the exact path
   tried** — a row asserting an equivalent does not exist is only worth having
   if it names what was searched.
2. Read the signature for a required `ctx: DeviceContext` and a `target`. That
   separates CPU ONLY from reachable, and nothing more.
3. **Run it against an independent host oracle** and put a verdict in the
   correctness table at the top of this file, with the sizes and the date.
   Add the check to `checks/vendor_correctness_check.mojo` so the next
   person regenerates the row instead of trusting it. Scattered hashed
   fixture, sizes straddling the block width, oracle computed independently.

A row that stops after step 1 or 2 is a row about REACHABILITY. It may not be
cited as a reason to use anything.

whether an import resolves and stopping there. The import resolving tells you a

corrections were cases where the capability was present and the guessed path

`nn.cumsum[exclusive]` for a symbol searched as `cumsum_exclusive`, and
