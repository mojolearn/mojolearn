Can the checks become grep?
--------------------------
For pure native trees, a small lexical rule plus transitive import closure is a
useful, simple invariant. The current layout guard already implements that idea,
stripping comments/docstrings and rejecting Python API/provider dependencies.
Keep it independent of large estimator runtime matrices and consider extending
approved native root coverage as migration completes.

At the boundary, plain grep cannot distinguish retaining a Python buffer owner
from calling its __array__, __int__, property or callback. Native C calls can
dispatch Python; PythonObject can also be passive ownership. A literal grep
would both report harmless documentation/allowed handles and miss indirect
callback dispatch. Preserve three small complementary layers:
  1. Native tree dependency/token guard.
  2. Public wrapper AST/installed-entry checks and focused transitive boundary
     review: fixed native dispatch, exact protocol admission, one per-operation
     metadata snapshot, no callback before admission.
  3. Bounded public runtime smokes plus hostile-protocol counters, profiling and
     approved-exception accounting, on the actually loaded artifact.

_verify_native_runtime.py already checks one wrapper, further Python frames,
forbidden/unresolved native origins and unobserved threads. It explicitly warns
that CPython audit hooks can evade profiler events; profile silence alone is not
proof. Source string assertions (including one textual metadata read) likewise
do not establish an actual once-only read at runtime.

Allowed categories must remain explicit: import-time package connection, tests,
scikit-learn tag-only metadata, passive/native buffer ownership, and documented
owner-approved Mojo interoperability exceptions. An exception must retain its
actual public-operation evidence and must never be labeled Python-free. The
native dictionary API repair in bindings/native_instance_item.mojo is legitimate
boundary handling, not a reason to reject every occurrence of PythonObject.
