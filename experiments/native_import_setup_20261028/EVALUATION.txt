Per-element conversion tags:
An outer exact-list check only admits container access. It does not establish
that elements share a class, dtype, or conversion rule. Do not classify the first
element and apply that rule to the rest. A safe operation-local plan observes
each element's exact type, caches classification by that native identity, and
still performs per-value range/NaN/shape checks and ordered refusal. Storage
buffers can instead admit a homogeneous native dtype/layout once and decode
all elements with its fixed tag, while retaining an actual buffer export.

Concrete application in this batch: _class_weight_rows resolves
labels_primitive_kind once per encountered exact scalar class, converts each
weight to Float64 once, and retains the native Float64 values for narrowing.
Each element still receives its own classification lookup, finite/sign check,
original-value equality test, and Float32 representability check. The input
values list owns all scalar/type identities while the native map is consulted.
The validation loop holds the GIL and invokes only admitted native scalar
conversions/comparisons; the cache does not span compiled numerical calls.
Balanced counts and weights also capture owner-backed pointers before their
class loops, removing repeated classical_address/Int conversions.

Higher-frequency follow-up, not changed here:
classical_labels.mojo:_sorted_classes (base lines 741-763) calls _label_kind ->
labels_primitive_kind per input label. That helper rereads canonical builtins,
integer/scalar type sequences and NumPy dtype aliases. Reuse an operation-local
exact-type classification table for this N-label pass, keeping per-value NaN
checks and mixed-string/number refusal. This shares the mechanism demonstrated
on class weights without treating mixed containers as homogeneous. Native
buffer decoding in native_scalar_decode.mojo already separates dtype metadata
from value bytes; a future batch decoder can reuse a captured dtype recipe and
export, but singleton callers must keep their individual owner/shape checks.

Why defensible without measuring:
All changes eliminate duplicated work or import/callback dispatch at an existing
setup boundary. None changes a numerical kernel, reduction order, default,
threshold, vendor path or arithmetic shortcut. No claim that source counts equal
hot-path costs or that these repairs guarantee an end-to-end speedup.
