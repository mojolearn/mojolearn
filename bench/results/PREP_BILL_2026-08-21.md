# train()'s preparation bill: 24 s around 0.75 s of trees -- the user-facing hole

2026-08-21, M4 base, `mojo_only/quantize_cost_probe.mojo` from a clean
worktree at `5eed329`. 400k x 500 raw float slice of epsilon, 20 trees
depth 6 @128, `train()` end to end against fit-only on prebuilt
fixtures, interleaved, 2 reps:

    train() end-to-end   24.52 / 25.07 s
    fit-only              0.75 /  0.77 s
    PREP BILL            23.77 / 24.30 s   -- 32x the training it feeds

Every benchmark row in this repository quantizes OUTSIDE the timed
region on both arms, which is correct for kernel comparisons and is
CatBoost's own courtesy convention here. But a user's `train(X, y)` --
and the Python `GradientBoosting.fit` above it -- pays this bill inside
the call, against CatBoost's multi-threaded C++ quantizer (single-digit
seconds at this shape). END TO END, TODAY, THE LIBRARY LOSES ON THE
FLAGSHIP SHAPE IT WINS 2-4x ON TREES, entirely on host-side
preparation.

## What the 24 s contains (components NOT yet individually measured)

1. GreedyLogSum border building: the exact DP per feature over the FULL
   400k values. TO CHECK AGAINST THEIR SOURCE: CatBoost builds borders
   on a bounded SUBSAMPLE by default -- if so, full-N DP is both a
   deviation and the likely dominant term.
2. Host binning: searchsorted per cell, 200M cells, single-threaded.
   The DEVICE binarize kernel (`binarize_float_feature_kernel`, ported
   for the inference path) already exists and is not wired into
   `train()`.
3. Host cindex staging: a per-feature host loop + copy + sync, 200M
   stores.

## Decomposed further, same day

One 400k column: `best_split` 45.9 ms unsorted, 11.8 ms on PRESORTED
input -- the internal shell sort is 34 ms (74%) and the DP 11.8. Their
GPU pipeline's own answer (`gpu_binarization_helpers.cpp:6-28`,
`ComputeBorders`) is a DEVICE RadixSort then the DP on the sorted
readback, full data, no subsample -- which our ported radix sort can
mirror with a host-side monotone float<->u32 twiddle in the staging
loops that already touch every element. Predicted: 24 s -> ~7 s serial,
~2.5 s with their per-feature executor parallelism. IMPLEMENTATION
PARKED mid-flight 2026-08-21 (cross-GPU identity work took priority);
the bit-identity gate for whoever resumes: the probe's recorded train()
mse 0.7658459375 must reproduce exactly, because the sorted multiset --
and therefore every border -- is unchanged.

## Step 1 LANDED, same day: the device sort, gated bit-identical

`DeviceFloatSorter` (gpu_util/kernel/radix_sort.mojo) is their
`ComputeBorders`' RadixSort with hoisted scratch -- the per-call
buffer-churn variant CRASHED the runtime on an early iteration of 500
calls, the preallocated shape survives 500 x 400k sorts verified
ascending in 6.6 s. Wired into `train()`'s float arm ahead of
`calc_quantization`. Same-window baseline vs candidate:

    prep bill  28.4 / 35.0 s  ->  18.8 / 18.9 s
    train mse  0.76594453125  ==  0.76594453125   (bit-identical, the
    sorted-multiset gate)

The remaining ~18.9 s decomposes as ~5.9 s of DP-on-sorted (11.8 ms x
500) and ~13 s NOT yet attributed -- the suspects are train()'s own
List append loops (column materialization and the 200M-element flat
pack), not arithmetic. Measure before touching, as ever.

## Steps 2 and 3 LANDED, same day: the overlap and the parallel DP

Two restructurings of the border build, each gated on the same
bit-identity (train mse 0.76594453125 reproduced exactly through both):

* **The overlap**: the sorter split into begin/finish, and the loop
  enqueues column g's device passes BEFORE running column f's DP -- one
  in-order queue, enqueue ahead, drain late. Border 12.4 -> 9.6 s.
* **The parallel DP** (their per-feature executor design,
  `calcBordersAndNanMode` on `NPar::LocalExecutor`): phase A pipelines
  every float column's device sort into one flat buffer; phase B runs
  every column's `calc_quantization` under `sync_parallelize` with
  disjoint flat output slots, the device never touched inside the
  parallel region (mojotrees' recorded deadlock rule), errors carried
  out through per-slot flags and re-raised after the join. Border
  9.6 -> 4.9 s; the 6.1 s serial DP folds to ~1.6 s.

The 200k x 2000 full-width row (`eps2000h` fixtures; 400k x 2000 needs
~12 GB resident for the shared process and is NOT honestly runnable on

    ours alone    7.4 s   (prep 5.8: phase B 2.76, cindex 1.69,

                           fit ~1.6)
    theirs alone  5.9-6.8 s
    honest standing at 200k x 2000: ~0.8-0.9x, separate-window caveat

THE PROTOCOL FINDING: one-process interleaving -- the rule that caught
the thermal and loaded-window lies -- ITSELF lies when the two arms'
combined footprint (~8-9 GB here: their row-major cache + our
column lists + both workspaces) crowds RAM. Our arm ran 3.5-4x slower
inside the shared process than alone; theirs 2-3x slower, climbing
rep to rep as caches warmed. Pageouts barely moved (2.4k pages) -- the
mechanism is compression/eviction pressure, not swap, so a pageout
check alone does not clear a window. RULE AMENDMENT CANDIDATE: an
interleaved row is valid only while combined resident set stays well
under physical RAM; above that, isolated per-arm runs with the
cross-window caveat stated are the less-dishonest number.

The old prediction that 2000 features already favor us end to end is
FALSIFIED at 200k rows and deleted above. Width helps the fit (the
four-axes law is real for kernels) but prep scales in features too --
phase B and cindex are per-feature -- so the prep bill grows with the
same axis that amortizes the fit floor.
