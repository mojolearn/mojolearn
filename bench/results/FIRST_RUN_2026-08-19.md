Apple M4. 3 rounds, alternating processes, 15 samples per arm per side, all
pooled from one invocation of `bench/run_bench.py`.

    knn               21.67        34.48     1.59x  INDISTINGUISHABLE

    pca               16.94         6.45     0.38x  sklearn faster

32, k=10. pca 200k x 32 -> 8. dbscan 4k x 16, eps 0.35. ols 500k x 32.

## Read this before reading anything else

**We lose three of five, tie one, and win one.** That is the result and it is
not softened anywhere in this repository.

## Why, and it is one cause

**Our GEMM.** `core/gemm.mojo` is a plain 16x16 shared-memory tiled product
written to be honest rather than fast, and its docstring says so. k-means,
k-NN, PCA and DBSCAN are all dominated by it.

On the other side is **Apple Accelerate**, which is what scikit-learn's BLAS
resolves to on this machine, and which dispatches matrix multiply to the
**AMX** coprocessor. That is dedicated matrix hardware on the CPU die. So the
comparison here is not "our GPU against their scalar CPU loop". It is our
untuned GPU kernel against Apple's hand-tuned matrix accelerator, and losing
that is not surprising.

This is the caveat recorded before the run, now measured: **we inherit the
incumbents' ARCHITECTURE and not their KERNELS.** cuBLAS, cuSOLVER, CUB and
CUTLASS are closed or CUDA-only, and that is where a large part of their
performance lives.

## The one win is partly an ALGORITHM difference, not a hardware one

OLS at 3.85x looks like the strongest result and it is the one to be most
careful about. scikit-learn's `LinearRegression` uses LAPACK `gelsd`, an SVD
of the full 500000 x 32 matrix. Ours forms `A^T A`, a 32 x 32 matrix, and
eigendecomposes that. Normal equations are simply less work than an SVD.

So we are partly winning on solver choice, which is a choice cuML also
offers (`algo=1`) and scikit-learn does not expose. It is a real win for a
user and it is NOT evidence that our kernels are fast. Compared against
sklearn's own normal-equations path the margin would be much smaller.

## What this says to do next, and it is not "port more algorithms"

Adding a seventh algorithm on top of this GEMM produces a seventh slow
algorithm. Every arm except OLS is GEMM-bound, so one kernel is worth more
than any number of ports.

The GEMM is the first thing this repository has measured that clearly
deserves optimization, and by the standing rule optimization was blocked
until a number existed. **The number exists.** COPY-DO-NOT-IMPROVE has done
its job: it produced a faithful baseline and a diagnosis, and the constraint
lifts for `core/gemm.mojo` specifically.

Candidates, in order: wider register tiles so each thread computes a 4x4
block instead of one element, vectorized loads, and a `k`-blocked layout that
keeps the accumulator in registers. None of these touch any algorithm.

## What was NOT measured

Accuracy. Every number here is wall-clock on data whose answer we already
check elsewhere. Nothing in this file says our answers are as good, only that
they are produced more slowly.
