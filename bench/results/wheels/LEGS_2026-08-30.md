## The two vendors' MAX runtime closures are BYTE-IDENTICAL

Compared across the two legs' manifests, all four staged libraries:

    libKGENCompilerRTShared.so   731a617b519a7a7b...  same on both
    libAsyncRTMojoBindings.so    ad566357627747cb...  same on both
    libMSupportGlobals.so        8c91d4c4c36405f8...  same on both
    libAsyncRTRuntimeGlobals.so  849571b9373a423b...  same on both

`docs/LINUX_WHEEL.md` section 9 listed this as unknown and `pack_wheel.py`
was written to decide the layout FROM the answer rather than assume one. It
chose `shared mojolearn/.libs`, which is 3.2 MB saved over shipping the
closure twice. `driver_libs_not_staged` is empty on BOTH sets: nothing
driver-side is bundled, because the extensions carry no `DT_NEEDED` on
`libcuda` or `libamdhip64` at all. MAX dlopens them, which is also why the
selector's probe has to load them with `ctypes.CDLL` rather than read an
ELF header.

## The packed wheel, and the manylinux level nobody had measured

    mojolearn-0.3.0-py3-none-linux_x86_64.whl     26,205,942 bytes packed
    cuda extensions 64.1 MB + hip extensions 42.2 MB + one 3.2 MB .libs
    auditwheel show: "consistent with manylinux_2_35_x86_64"
    mojolearn.libs entries after repair: 0

**The measured floor is `manylinux_2_35_x86_64`**, not a guess and not a
number typed into `pack_wheel.py`, which writes `linux_x86_64` on purpose
because PyPI refuses it. It is driven by `GLIBCXX_3.4.30` and `GLIBC_2.34`
in the versioned symbols the extensions reference, which is the Ubuntu 22.04
toolchain both boxes run. glibc 2.35 means Ubuntu 22.04 and Debian 12 are
in; RHEL 9, on glibc 2.34, is OUT BY ONE MINOR VERSION. Lowering the floor
means building on an older base image, and that is a future leg, not a
retag.

`auditwheel repair` DOES honor `--exclude` for libraries it resolves through
`$ORIGIN`: zero `mojolearn.libs/` entries in the repaired wheel, so the
staged closure is not shipped a second time. That was listed as unverified
and is now measured.

## A third gate had the same pipefail bug, and it hid itself

`audit.sh` ended its repair step with

    unzip -l "$r" | grep -c 'mojolearn.libs/' | sed 's/^/... /'

and `grep -c` EXITS 1 WHEN THE COUNT IS 0. Zero is the wanted answer, so
under `set -euo pipefail` the script killed itself on success, one line
before `twine check`, and left no `twine.txt`. The run still looked clean
because the caller read a pipeline's exit code rather than the script's.
The count is now taken with `|| true` and asserted separately, so a NON-zero
count is a named failure instead of a line of output nobody reads.

This is the same shape as the bug found the same morning in the release
workflow's Digest step, where `ls *.whl | grep -v -- '-macosx_'` exits 1 on
a macOS-only release. Two independent instances in one morning is a pattern
worth naming: **a `grep` whose zero-match case is the SUCCESS case must not
sit in a pipeline under `pipefail`.**

## `nogpu` FAIL is a defect in the gate, and it could never have passed

The `namespace` route ran for the first time (the droplet is a VM, so
`unshare` is not refused the way it is inside the RunPod container). It hid
`/dev/kfd`, `/dev/dri/renderD128` and two `libamdhip64.so*` paths by
bind-mounting `/dev/null` over each, then imported, and the import
SUCCEEDED reporting `hip`.

**A bind mount leaves the path existing.** The probe asks
`os.path.exists("/dev/kfd")`, and a `/dev/kfd` that IS `/dev/null` still
exists. Demonstrated directly, in a privileged container:

    before bind: True
    after  bind: True     <-- the old gate expected False

So the route reported FAIL against a library doing exactly the right thing,
and no possible library behaviour could have made it pass. Fixed by
replacing the technique rather than the expectation: a tmpfs holding only
`null`, `zero`, `full`, `random`, `urandom`, `tty` and `ptmx` is mounted OVER
`/dev`, so every other node under it is genuinely gone, and `/dev/null` is
still bound over the driver libraries, which is the correct technique for
THEM because the probe loads a library rather than stat-ing it. Verified the
same way:

    BEFORE  /dev/kfd exists: True
    AFTER   /dev/kfd exists: False | /dev/null usable: True
    ImportError: mojolearn: NO SUPPORTED GPU FOUND ON THIS BOX

## Gate (d) is CLOSED, and it never needed a rented box

`docs/LINUX_WHEEL.md` section 9 has carried "whether the RunPod image honors
`unshare -rm` for gate (d)" as unverified since the design. It is the wrong
question. Both rented boxes are the WRONG PLACE to ask what happens with no
GPU: the RunPod pod is a container with no docker daemon and seccomp-refused
`unshare`, and the DigitalOcean image ships without docker. A box with no GPU
is the one thing neither can be.

This Mac can be one, for the price of a container.
`packaging/linux/nogpu_local.sh` builds a package root from the tracked `.py`
files and a FETCHED set and imports it in `python:3.12-slim` on
`linux/amd64` with no device passed through. Against the MI325X's hip set:

    ImportError: mojolearn: NO SUPPORTED GPU FOUND ON THIS BOX, and there is
    no CPU path in this package. This install carries binary sets for ['hip']
      cuda:  /dev/nvidiactl absent  /dev/nvidia0 absent
             libcuda.so.1 not loadable   libcuda.so not loadable
      hip:   /dev/kfd absent  /dev/dri/renderD128 absent
             libamdhip64.so.7/.6/.so all not loadable
      MOJOLEARN_VENDOR is not set.

    nogpu_local PASS (import refused, rc=1, every probed name printed)

The gate reads the probed names OUT OF `_backend._PROBE` rather than
retyping them, so a path added to the probe and left out of the message is a
FAIL. Sabotage-checked: bypassing the probe with `MOJOLEARN_VENDOR=hip` turns
it red on four separate lines, and it stays red with the exit-code check
removed.

## NARROWED: `MOJOLEARN_VENDOR=hip` ABORTS instead of raising when ROCm is
## entirely absent. It is not an ISA problem, and it is not on the default path.

Installing the finished `manylinux_2_35` wheel in `python:3.12-slim` on
`--platform linux/amd64` (Docker Desktop on Apple silicon):

    pip install                      OK
    import mojolearn                 refuses correctly, names both sets
    MOJOLEARN_VENDOR=metal           refused by name, correct
    MOJOLEARN_VENDOR=cuda            imports; the FIT then RAISES cleanly:
                                     Failed to open library "libnvidia-ml.so.1"
    MOJOLEARN_VENDOR=hip             Illegal instruction (132), AT IMPORT

The two forced arms are the whole finding. With no device of either kind,
**cuda degrades correctly and hip aborts the process**, and hip does it
during module init, before a fit can even be attempted.

### The ISA theory was tested three ways and is DEAD

The first reading was that the hip set had been built for a wider ISA than
the emulated CPU provides. Every part of that is now ruled out:

* A C program using `_mm512_add_ps`, compiled `-mavx512f`, RUNS under this
  emulation and prints its result. **AVX-512 is available here.**
* Neither set contains a single instruction from the newer AVX-512 subsets
  that an emulator would be likelier to miss: no `vdpbf16ps`, `vpdpbusd`,
  `vpdpwssd`, `vp2intersect`, `vgf2p8*`, `vaes*` or `vpclmul*` in either.
* `ud2` appears **59 times in the cuda set and 58 times in the hip set** --
  essentially the same. "Illegal instruction" is what an executed `ud2`
  looks like, and both binaries are full of them, so the signal says
  ABORT PATH TAKEN, not CPU FEATURE MISSING. An ISA gap would also not
  explain why cuda, built from the same source by the same toolchain, is
  fine on the same CPU.

There is no `cpuid`, `xgetbv` or `xsave` in either set, so there is no
runtime feature dispatch to have gone wrong either way.

### What this means for the wheel

**It is not on the default path.** With `MOJOLEARN_VENDOR` unset -- which is
how the library is meant to be used, and what every user gets -- the probe
runs first and refuses with the full table before any binary is called. That
refusal is verified against this same wheel.

It is reached only by explicitly overriding the probe on a box that does not
have that vendor's device. That is not a hypothetical: the refusal message
itself offers `MOJOLEARN_VENDOR=cuda or MOJOLEARN_VENDOR=hip` as the escape
hatch for "if the device is present and this probe is wrong", and promises
that "the first fit reports the runtime's own error". **For hip that promise
is not kept**: the process dies at import with no Python traceback. For cuda
it is kept exactly.

So this is a real defect, narrow and low severity, and it is a defect in the
FAILURE PATH rather than in anything the wheel does when a device is there.
The same hip set ran 29 smoke lanes in each of the three tiers on the MI325X,
and on that box, with ROCm present but devices hidden, forcing hip raised a
clean `hipErrorNoDevice` exception rather than aborting. The difference is
whether the HIP runtime library exists at all, not whether a device does.

**Owed:** reproduce on real x86-64 hardware with no ROCm installed (this
observation is under emulation), then either make the hip init path raise the
way the cuda path does, or say plainly in the refusal message that forcing a
vendor whose runtime is absent can abort. Until then the message promises
something it does not deliver on one of its two branches.

## THE INSTALL LEGS, and the finding that stops the Linux wheel from shipping

0.3.0 went to TestPyPI with both wheels (`mojolearn-0.3.0-py3-none-macosx_11_0_arm64.whl`
and `mojolearn-0.3.0-py3-none-manylinux_2_35_x86_64.whl`). The macOS wheel
installs from TestPyPI into a clean venv on the M4 and fits in all three
tiers, `vendor metal`. Then the Linux wheel was installed from TestPyPI onto
an **NVIDIA A40**, chosen precisely because it is NOT the H100 PCIe that
built the CUDA set.

### The CUDA set is locked to the GPU architecture that built it

    index=testpypi  version=0.3.0  vendor=cuda  smoke_rc=1
    2 lanes passed of 29.

    lane tsvd: At max/mojo/max/gpu/host/_device_context_extras.mojo:168:17:
      CUDA call failed: CUDA_ERROR_NO_BINARY_FOR_GPU
      (no kernel image is available for execution on the device)

Twenty-seven of twenty-nine lanes, in all three tiers, with that error. The
two that passed say exactly what is wrong:

    gemm-vendor      ok   523f5d1954f7409c   0.2s
    gemm-pinned      ok   REFUSED as designed under fast

`gemm-vendor` calls MAX's own matmul, which reaches cuBLAS, a RUNTIME
library that ships with the driver and works on any supported device. It ran
and produced a hash. `gemm-pinned` refused, correctly, because `fast` makes
no cross-vendor claim. **Everything that launches one of OUR compiled kernels
failed, and the one thing that does not, worked.** The GPU is fine, the
driver is fine, the wheel installed, the vendor probe picked `cuda`
correctly, the binaries loaded, and the read-back agreed. There is simply no
sm_86 code in them.

`pip install` from an index onto a box that did not build the wheel is
therefore PROVEN to work, and so is every part of the selector. What is
proven NOT to work is running the result on a different NVIDIA generation.

### What this means

**The Linux wheel must not go to PyPI in this form.** `pip install mojolearn`
on any Linux box whose GPU is not an H100 would install cleanly, import
cleanly, report its vendor correctly, and then fail on essentially every
operation. That is worse than having no Linux wheel, because the failure
arrives after the user has been told everything is fine.

`docs/LINUX_WHEEL.md` section 9 has carried "whether a set built on one
NVIDIA architecture runs on another" as the biggest unknown since the design
was written, and the answer is NO, measured, on the first box that asked.

### The fix, and what is known about it

`mojo build` takes `--target-accelerator`, documented as one architecture
(`sm_90` for an H100, `gfx942` for an MI300). `build_sets.sh` passes it NO
target at all today, so MAX compiles for the build box's own device.

Measured about the flag, on the M4, at `40c2c5fc`:

* A repeated flag is REFUSED: `too many specified target accelerators,
  expected exactly one`.
* A COMMA-SEPARATED LIST is accepted by the parser and echoed back intact by
  `--print-effective-target` as `sm_80,sm_86,sm_90`, and a real
  `mojo build` of `ensemble/mojo_only/rf_ctx_order_probe.mojo` with that list
  SUCCEEDS.

That is not yet evidence that it EMITS code for each architecture. The two
binaries differ by 8 bytes on the Mac, which is what you would expect if no
CUDA device code was embedded in either, because the Mac's accelerator is
Metal. **The comma list parses and builds; whether it produces a fat binary
has to be measured on a CUDA box, by building with a list and then running on
a GPU that is not the builder.** That is the next leg, and it is the same
A40-after-H100 shape that found this.

The AMD side has the same question and no cross-generation box to ask it
with: DigitalOcean offers one AMD GPU model.

## `--target-accelerator` TAKES EXACTLY ONE ARCHITECTURE. The comma list is dead.

Measured on an A40 at `1e2a1c1`, `MOJOLEARN_GPU_ARCHS="sm_80,sm_86,sm_90a"`,
recorded in the leg's own `leg.txt` as `gpu_archs=sm_80,sm_86,sm_90a`:

    /root/mojolearn/bindings/_mojolearn.mojo:362:5: error: function
      instantiation failed
    std/gpu/host/info.mojo:2145:5: note: constraint failed: GPU architecture
      'sm_80,sm_86,sm_90a' is not supported.
    mojo: error: failed to run the pass manager

The parser accepts a comma list and `--print-effective-target` echoes it back
intact, which is why it looked plausible on the Mac. The COMPILER treats the
whole string as one architecture name and rejects it. **One build, one
architecture.** There is no fat binary out of a single `mojo build`.

### The read-back earned its place on its first run

`build_rc=1`, and the architecture read-back added the same morning said
exactly what happened:

    27 sm_86
     3 MISSING

The three MISSING are `_mojolearn.so` in each tier, the one binding that
reaches the `info.mojo` constraint. **The other twenty-seven built happily and
came out as `sm_86`** -- the A40's own device, NOT the list that was asked
for. MAX ignored the unusable string and silently fell back to the detected
GPU. Without the read-back this leg would have produced twenty-seven binaries
that look built, report vendor `cuda`, and carry the wrong architecture, and
the only complaint anywhere would have been one binding failing to compile.
That is the same shape as the defect it was written for.

### There is no PTX either

Neither the sm_90a set nor the sm_86 set contains a single `compute_NN`
string. MAX emits no PTX, so there is no JIT path and no forward
compatibility: a binary runs on the architecture it was built for and
nothing else. `mojo build --print-supported-accelerators` lists concrete
targets only (`sm_52` through `sm_121a`, `gfx90a` through `gfx1201`); it
offers no generic or virtual architecture.

### What a portable Linux wheel therefore costs

One binary per architecture means the package needs an ARCHITECTURE AXIS
under the vendor axis, `mojolearn/<vendor>/<arch>/<tier>/`, chosen at import
from the device's compute capability. The size arithmetic, from this
release's measured numbers (cuda 64.1 MB, hip 42.2 MB, shared libs 3.2 MB,
all three tiers, compressing 4.18x into a 26.2 MB wheel):

    NVIDIA archs   AMD archs   uncompressed     packed     under PyPI's 100 MB
        1              1          109.5 MB      26.2 MB     yes (today)
        3              1          237.7 MB      56.9 MB     yes
        4              2          344.0 MB      82.3 MB     yes, tight
        5              2          408.1 MB      97.6 MB     no headroom

So four NVIDIA architectures (sm_80 A100, sm_86 A40 and RTX 30, sm_89 L40 and
RTX 40, sm_90a H100) plus two AMD (gfx90a MI200, gfx942 MI300 and MI325) fit
in about 82 MB, with no room left for Blackwell. Build time is N times one
build, which is 915 s each on an H100 and can run on N boxes at once.

**This is a design change, not a bug fix.** It touches the layout, the
selector, `pack_wheel.py`, and every gate that walks a set. It is not
attempted here, and the Linux wheel stays off PyPI until it is done or until
a narrower claim is deliberately chosen.
