# NVIDIA identity-cost grid: plan of record (2026-09-07)

One question, one grid. On one NVIDIA device, at large workloads, what does
mojolearn's IDENTICAL mode cost against the strongest incumbent GPU
implementation of the same algorithm, in that incumbent's FAST configuration
and in its DETERMINISTIC configuration, in time and in accuracy.

Our FAST and DETERMINISTIC modes are not in this grid. The only mojolearn arm
is IDENTICAL, carried to the box as `MOJOLEARN_NUMERIC_MODE=identical`
(DEVIATION 1898), compiled into every binding by `bindings/build*.sh`, read
back on every `FSPEED-HEADER` line, and refused at fetch time if any header
says otherwise.

## The grid

Rows: one row per (lane, dataset, row count). Columns:

| mojolearn IDENTICAL | incumbent FAST | incumbent DETERMINISTIC |
|---|---|---|
| median ms, [min,max], run-to-run hash, logloss/AUC or RMSE | same | same, or NOT-OFFERED with the vendor's own words |

Every arm alternates with every other arm inside one process, one lane per
process, one untimed warm-up then five timed rounds, on the same box, so a
box that throttles throttles every arm together and the ratio survives.

## Lanes and incumbents (one incumbent per lane, algorithm-matched)

| lane | mojolearn | incumbent FAST | incumbent DETERMINISTIC |
|---|---|---|---|
| gbdt-symmetric | GradientBoosting(SymmetricTree) | CatBoost GPU | NOT-OFFERED: "Training on GPU is non-deterministic, because the order of floating point summations is non-deterministic in this implementation." (catboost.ai, features/training-on-gpu) |
| gbdt-depthwise | GradientBoosting(Depthwise) | XGBoost device=cuda, tree_method=hist, grow_policy=depthwise | NOT-OFFERED: no documented deterministic parameter for hist on cuda (xgboost Parameters page); the FAST arm's per-round hash records whether it repeats |
| gbdt-lossguide | GradientBoosting(Lossguide) | XGBoost cuda lossguide; LightGBM CUDA where its learner builds inside the lease | XGBoost: NOT-OFFERED as above. LightGBM: NOT-OFFERED: `deterministic` is "used only with cpu device type" (LightGBM Parameters) |
| rf | RandomForest(device=gpu) | cuML RandomForest, n_streams=4 (default) | cuML RandomForest, n_streams=1 (the one configuration cuML's source calls reproducible) |
| et | ExtraTrees(device=gpu) | LightGBM CUDA boosting_type=rf, extra_trees=true | NOT-OFFERED (LightGBM, as above) |

Hyperparameters are `tools/speed_gbdt_arm.py::lane_config`, identical on every
arm: 100 trees, depth 6 (boosting) or 16 (forests), learning rate 0.1, L2 1.0,
254 borders = 255 bins, no row or column sampling, plain boosting, seed 7.

## Datasets: few features, many features, and a regression target

| dataset | task | features | rungs (training rows) |
|---|---|---|---|
| HIGGS | binary | 28 | 1,000,000; 2,000,000; 5,000,000 (nested prefixes, one fixed 500,000-row test tail) |
| YearPredictionMSD | regression | 90 | 463,715 (shipped) |
| synthwide | binary | 500 | 1,000,000 (deterministic generator, seed 7) |

## Legs (RunPod, NVIDIA H100 80GB HBM3, image runpod/pytorch:2.4.0-py3.11-cuda12.4.1-devel-ubuntu22.04)

One lane per leg so a lane that loses its lease loses only itself. Legs run
concurrently (`MOJOLEARN_LEG_ALLOW_CONCURRENT=1`); every leg has its own pod
name, its own dead-man on the pod, and its own sixty-minute hard cap.

| leg | lanes | ladder | LightGBM CUDA build |
|---|---|---|---|
| S | gbdt-symmetric | higgs:1M,2M,5M year synthwide:1M | no |
| D | gbdt-depthwise | same | no |
| L | gbdt-lossguide | same | yes (the lossguide incumbent's own algorithm) |
| F | rf | same | no |
| E | et | higgs:1M,2M synthwide:1M | yes (the only GPU ExtraTrees incumbent) |

Command shape, from the clean worktree on branch grid/nvidia-identity-2026-09-07:

    MOJOLEARN_RUNPOD_KEY_FILE=$HOME/.mojolearn_runpod_key \
    MOJOLEARN_LEG_ALLOW_CONCURRENT=1 MOJOLEARN_SPEED_OURS_MODE=identical \
    MOJOLEARN_SPEED_FAMILY=forest MOJOLEARN_SPEED_LANES="<lane>" \
    tools/gemm_remote_leg.sh nvidia --payload speed --family forest \
      --dataset "higgs:1000000,2000000,5000000 year synthwide:1000000" \
      --gpu "NVIDIA H100 80GB HBM3" --minutes 60 --rent [--no-lgbm-cuda]

## What comes home and where it goes

`bench/results/e1g/<stamp>-nvidia-speed-forest/remote/logs/forest.<lane>.<dataset>.r<rows>.log`
with the FSPEED contract (HEADER, WARMUP, round lines with ms and hash, ACC,
REFUSED, NOTE). `tools/identity_grid_json.py` reads every leg directory and
writes one JSON record with, per (lane, shape, arm): median, min, max,
rounds, distinct hashes across rounds, metrics, and the exact NOT-OFFERED
reason for absent deterministic arms. The paper binds its grid from that
record through `mlsys/paper/gen_numbers.py`; no number is typed by hand.

## What this grid does and does not say

It prices the present IDENTICAL implementations against mature CUDA
libraries on their own hardware, including our optimization gaps. It does not
isolate a universal cost of bitwise arithmetic, and a slower cell is a
measurement of a kernel, not of the contract. Where an incumbent offers no
deterministic configuration the cell says so in the vendor's words; that is
a finding about the vendor, not a blank. Accuracy is reported beside every
time so no speed is bought with an undisclosed quality loss.
