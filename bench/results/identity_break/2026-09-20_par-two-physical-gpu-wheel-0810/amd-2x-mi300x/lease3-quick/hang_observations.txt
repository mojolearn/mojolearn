What this establishes: two workers existed, so the one-device column had finished and the
two-device pool had started; the worker masked to device 0 then sat in a kernel GPU fence
wait for at least eleven minutes with the GPU idle, while device 0's VRAM was 99.7 % used
and one process held 392 GB across both devices. It happened the same way in all three
commands.

What it does not establish: the cause. `verify --par` runs both columns in ONE process; the
AMD two-device records on main came from tools/two_device_par_class_amd_leg.sh, which runs
each column in its OWN process. A parent that still holds nearly all of device 0 while a
masked worker starts on device 0 fits the samples, and is untested. The known MI300X SR-IOV
stale read (wrong values after a cross-device copy above 1 MiB) is a different symptom and
nothing here points at it. The same wheel and the same commands pass on 2x RTX 4090.
